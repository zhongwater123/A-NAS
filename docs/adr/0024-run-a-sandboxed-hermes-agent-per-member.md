# 0024：AI 助手以每个账号一个沙箱中的 Hermes Agent 运行

状态：proposed（2026-10-14 与用户讨论后起草；同日在开发机完成 spike，含 DeepSeek 真实模型测试与助手窗口原型；实验 NAS 上尚未验证）。2026-10-15 对照上游后用户决定：助手与 Hermes 之间改用官方 Desktop 所用的 `hermes serve`（REST 加 `/api/ws` 上的 JSON-RPC），写入确认改用 Hermes 的回合内审批；决定 4 已按 [#111](https://github.com/zhongwater123/A-NAS/issues/111) 的验证改写，决定 6 已按 [#113](https://github.com/zhongwater123/A-NAS/issues/113) 的验证细化，决定 9 已按 [#109](https://github.com/zhongwater123/A-NAS/issues/109)、[#110](https://github.com/zhongwater123/A-NAS/issues/110) 的验证改写；同日用户决定加入会话闸门（决定 10）。2026-10-16 用户决定只拦能做出破坏性操作的，其余工具尽量让助手用：决定 8 已改写，决定 4 增加复制与命令卡片。行为见 [AI 助手规格](../specs/ai-assistant.md)，外部事实见 [Hermes Agent 可行性研究](../research/hermes-agent-runtime.md)。

AI 助手需要记忆、技能、多模型与工具调用这些智能体能力，自己实现等于重写一个成熟框架；但 [Hermes Agent](https://github.com/NousResearch/hermes-agent) 是为单一主人设计的，默认带终端与文件的全部权限，而 A-NAS 有多名成员，文件只由内核 ACL 授权。我们决定：以 Hermes Agent 为运行时，每个账号运行一个独立实例，由 systemd 沙箱只给它看本人能读的几处位置，只让它自由写自己的助手目录；对个人空间与 Agent空间的更改先写入暂存区，只有账号本人在自己的会话中确认后才由文件代理执行。权限由内核与 A-NAS 强制，不依赖 Hermes 的配置或模型的自觉。

## 决定

1. **运行时**：固定 Hermes Agent 的一个提交，在开发机构建运行环境，按内容存放在 `/opt/a-nas` 并由 release 引用，设备上不运行 pip、不联网、不自更新（与 [ADR 0016](0016-ship-photo-ai-as-a-built-in-offline-capability.md) 相同）。与相册 AI 不同，运行环境自带 CPython 3.14（Hermes 的依赖只在 3.14 上安装，Debian 13 是 3.13），依赖按上游 `uv.lock` 以哈希固定，Hermes 本身以固定提交的源码可编辑安装（上游拒绝构建 wheel）。A-NAS 只经 `hermes serve` 的接口（REST 与 `/api/ws` 上的 JSON-RPC，与 Hermes Desktop 相同）与 MCP 对接 Hermes，不 import 它的内部代码；更换运行时不影响 A-NAS 侧的模型网关、MCP 工具与确认流程。
2. **每个账号一个实例**：模板单元 `anas-assistant@<账号>.service` 以该账号本人的 Linux 身份运行，附加组为 `a-nas-users`；管理员的实例还带着 `a-nas-admins`（systemd 按 `User=` 从 `/etc/group` 取附加组，单元中去不掉），所以要求沙箱能接触到的东西都不授予 `a-nas-admins`，由探针持续检查（[研究](../research/hermes-agent-runtime.md#真实安装器布局上的沙箱1152026-10-15开发机)）。内核 ACL 决定它能读什么，与文件工作进程和终端一致（[ADR 0008](0008-use-unified-linux-identities-and-filesystem-acls.md)）。同一 UID 带来的风险由沙箱封住：独立 PID 命名空间（`PrivatePIDs`）、禁止 ptrace 一类系统调用、私有 IPC 与 keyring、没有任何能力。PID 命名空间中的 1 号进程是 `tini`，由它回收孤儿进程。实例由每个账号的 Unix 套接字按需启动：套接字触发的 `systemd-socket-proxyd` 以 `JoinsNamespaceOf=` 进入实例的网络命名空间，转发到它的 `hermes serve`，最后一条连接断开 45 秒后退出并带走实例（`StopWhenUnneeded`）。成员登录 WebOS 时，产品服务就经文件代理打开一条到实例的连接并保持到这个成员的全部会话结束，所以实例从登录起在后台启动并常驻，打开助手不再等冷启动（用户 2026-10-19 决定，[研究](../research/hermes-agent-runtime.md#登录即启动并常驻2026-10-19开发机)）。这些套接字只有 root 能连接，产品服务经文件代理取得连接（决定 10）。每个实例另有一个随机的会话令牌（`HERMES_DASHBOARD_SESSION_TOKEN`），由 root 写入只有 root 能读的文件，systemd 在降权前读入；文件代理随连接把它交给产品服务，产品服务不在磁盘上保存它。
3. **沙箱只挂三处**：本人的个人空间（只读）、共享空间（只读，含 Agent空间）与本人的助手目录（读写，唯一可写处）。助手目录分成两处挂载：Agent 的工作区 `/nas/助手`，以及工作区之外、文件工具写不到的 Hermes 状态目录；Hermes 启动时会加载代码或设置的 `config.yaml`、`.env`、`SOUL.md`、`hooks/`、`plugins/` 是 root 所有的只读文件，因为能写这些位置就等于能在实例中执行代码或改写每次的系统提示；两处空间的回收站在沙箱中各是一个只含本人文件夹的空 tmpfs，他人的回收站文件夹既读不到也看不见（看得见却读不了的文件夹会让 Hermes 的 ripgrep 搜索整体失败）；数据卷其余部分、快照、系统盘上的状态都不在沙箱中。实例没有网络（`PrivateNetwork`），唯一出口是经绑定进来的 Unix 套接字回到产品服务的模型网关与 MCP 端点（实例内由 `socat` 从回环地址转入），以及相册服务的助手套接字（决定 6）；产品服务按请求来自哪个实例的套接字认定账号，Hermes 不持有任何 A-NAS 令牌或模型密钥。
4. **写入**：Hermes 自带的文件工具与终端直接写助手目录。对个人空间或 `Agent空间/<本人>` 的新建、修改、移动、改名与删除，先写到助手目录内的暂存区，再调用 MCP 工具“提交更改”；复制（文件或整个文件夹，来源是助手能读的个人空间、共享空间或助手目录）不经暂存，由执行方以成员身份复制，所以图片、视频等任何大小的文件都能复制。managed scope 把 A-NAS 的 MCP 服务器设为 `trust: untrusted`，这个工具没有 `readOnlyHint`，所以 Hermes 每次调用它之前都在这一回合内请求审批，与 Hermes Desktop 的审批相同（[研究](../research/hermes-agent-runtime.md#回合内审批1112026-10-15开发机)）。产品服务按回合中这次调用的参数生成确认卡片，卡片只属于发起它的对话，成为一份[待确认更改](../../CONTEXT.md)；成员拒绝、在 managed scope 固定的 `approvals.timeout` 内没有回答，或停止这一轮，都按拒绝处理，什么都不改变，也不跨回合保留；助手在同一回合中得到结果。只放行“确认一次”与“拒绝”，不提供 Hermes 的“本会话”与“始终”。Hermes 转来的同意不足以执行：成员在本人的 Web 会话中点确认时，产品服务带着这个会话的令牌请执行方登记一次性授权（账号、更改、参数摘要），执行方自行确认会话有效且属于这个成员（决定 10），之后产品服务才应答 Hermes；“提交更改”到达执行方时，只执行本人授权过、参数相同、没用过且没过期的更改，写入的是生成卡片时复制的暂存内容，目标在此后变化即拒绝。生成卡片时读取目标与暂存内容（同样要本人的有效会话）、确认后执行，都由文件代理以本人身份进行，不经过路径中的任何链接（包括成员自己建的）；删除与被覆盖的旧版本进入本人的回收站，按 Samba `recycle` 的布局放在原文件夹下；执行进程由 Landlock 限制为只能写这两处，以及共享空间中本人的回收站 `spaces/shared/.a-nas-trash/<账号>`（Agent空间中被删除或覆盖的文件放在那里）。共享空间的其他位置无论确认与否都不能写。
5. **Agent空间**：`共享空间/Agent空间` 由 Host Agent 预建并修复，全体成员只读；每个账号在其中有一个只授本人 `rwx` 的子目录，与 `.a-nas-trash/<username>` 的 ACL 模式相同（[存储与文件架构](../architecture/storage-and-files.md)）。它与成员子目录是保留名：产品服务拒绝在 Web 上对它们改名、移动与删除；SMB 上的改名拒绝不了，由 Host Agent 对账修复，把位置上的冒名目录连同其中他人建的子文件夹挪开后重建，不原地接管（[研究](../research/hermes-agent-runtime.md#真实安装器布局上的沙箱1152026-10-15开发机)）。
6. **相册**：照片不是普通文件，助手经 MCP 只读工具访问相册服务；`photos.Principal` 增加助手标记，相册服务据此只允许读取，去掉管理员身份与查看授权，范围为本人的私有图库与共享图库（[ADR 0011](0011-run-the-photo-library-as-a-dedicated-service-identity.md)），也不替成员创建私有图库。助手没有会话，而相册服务不信任产品服务声明的身份（ADR 0011 决定 4），所以照片工具不经产品服务，产品服务也不持有任何能读私有图库的身份：相册服务另开一个助手套接字，沙箱中的 MCP 服务以成员本人的 UID 连接，相册服务从内核的对端凭据得到 UID，经 Host Agent 确认是在用账号后才构造助手 Principal。这个套接字所在目录只有相册服务能进，由 systemd 只绑定进助手沙箱，并且只开放工具用到的读取路由，没有原图和缩略图。工具交给模型的只有名称、拍摄时间、图库、标签与相册，不交出像素；managed scope 固定 `agent.image_input_mode: text`，配置了支持视觉的模型也不会把图片发给它。窗口凭工具结果中的照片编号，用成员自己的会话显示缩略图（[研究](../research/hermes-agent-runtime.md#相册只读访问1132026-10-15开发机)）。产品服务被攻破时，经助手只能读到正在登录的成员的照片元数据（决定 10），与 ADR 0011 一致。
7. **模型**：产品服务提供 OpenAI 兼容的模型网关并持有密钥。开发期转发到云端 API，仅用于开发测试；之后换成设备上的本地多模态模型，Hermes 一侧的配置不变。
8. **固定策略与开放的工具**（用户 2026-10-16 决定：只拦能做出破坏性操作的，其余尽量让助手用）：模型地址、启用的工具与各项关闭写在 root 所有、沙箱内只读的 Hermes managed scope（`/etc/hermes`）中，Agent 自己的配置无法覆盖。启用 Hermes 自带的 `file`、`terminal`、`code_execution`、`delegation`、`clarify`、`vision`、`video`、`memory`、`session_search`、`skills`、`todo` 与 A-NAS 的 MCP 工具，关闭 `tool_search`，让 A-NAS 的工具直接出现在模型的工具列表中。终端与代码以成员本人的身份在沙箱中运行：个人空间与共享空间是只读挂载，没有网络，看不到他人与系统，能写的只有助手目录和它的 Hermes 状态。Hermes 自己的审批照常：`approvals.mode: manual` 下危险命令与每段 `execute_code` 代码都先问成员，产品服务把它们显示为命令卡片（决定 4 的确认卡片之外的一种，不经执行方），`clarify` 的问题显示为问题卡片。关闭的只剩：需要网络的（`web`、`search`、`x_search`、`browser`、`tts`、`image_gen`、`video_gen`、`connections`，沙箱没有网络，另行决定）、需要桌面或别处账号的（`computer_use`、`desktop_ui`、`project`、`onboarding`、`bot_room`、`kanban` 与消息平台）、会装代码或在成员不在时运行的（`catalog`、`cronjob`），以及 Nous Tool Gateway、Honcho、`smart` 审批的辅助模型、更新检查、模型目录拉取、运行时装包与语言服务器。`vision` 与 `video` 会把图片与画面发给模型，只用于测试，直到本地模型（决定 7）。实例的会话令牌按 Hermes Desktop 经 SSH 交给后端的方式，以只有本人可读、读后即删的文件交给 `hermes serve`（`--ssh-session-token-file`），任何进程的环境中都没有它，`serve` 自己不可转储，所以终端读不到它（[研究](../research/hermes-agent-runtime.md#开放-hermes-自带的工具2026-10-16开发机)）。
9. **界面**：AI 助手窗口是 A-NAS 自己的桌面应用，走 Hermes Desktop 的通道：产品服务的 `/api/v1/assistant` 提供一条 WebSocket，按白名单逐帧转发成员实例上 `hermes serve` 的 JSON-RPC，方法与参数、事件、服务端请求都只放行列出的，其余由产品服务直接拒绝；另有对话列表、历史、改名与删除的 REST 路由（[白名单](../research/hermes-agent-runtime.md#白名单第一版)）。审批从不原样转发：产品服务把它对应到“提交更改”、生成确认卡片，成员的回答经单独的接口回到产品服务，由它按决定 4 核对后自己应答 Hermes。对话区复用 Desktop 的代码，不另写：assistant-ui 渲染，Desktop 的会话记录模型（`src/lib/chat-messages`）与它的 JSON-RPC 客户端（`apps/shared` 的 `json-rpc-channel`、`json-rpc-gateway`）按固定提交复制进 [`web/src/assistant/hermes`](../../web/src/assistant/hermes/README.md)，依赖版本与 Desktop 的锁文件一致。对话列表、确认卡片、样式与对话的连接逻辑是 A-NAS 的。不嵌入 Hermes 自带的网页控制台，也不嵌入整个 Hermes Desktop。
10. **会话闸门**（用户 2026-10-15 [决定](https://github.com/zhongwater123/A-NAS/pull/121#issuecomment-6186654287)）：产品服务自己连不到任何成员的实例，也不能凭自己登记授权。它每次要连到某成员的实例，都把这次请求所在的登录会话的令牌交给文件代理；文件代理像对待文件操作一样自行查会话表，确认会话有效、账号在用且正是这个成员，再以 root 连接该成员的实例套接字，把已连接的描述符与实例的会话令牌交回产品服务，与管理员终端（[ADR 0008](0008-use-unified-linux-identities-and-filesystem-acls.md)）的做法相同。文件代理留着这条连接，每 30 秒复查一次会话，会话失效（退出登录、过期、账号停用）就切断它。决定 4 中生成卡片与登记授权同样要成员本人的有效会话。所以产品服务被攻破时，经助手能读写的只剩正在登录的成员，与文件和相册（[ADR 0011](0011-run-the-photo-library-as-a-dedicated-service-identity.md)）的威胁模型一致；会话表由产品服务写入，这一点对三者相同。

## 后果

- **隐私（暂不处理，只在此注明）**：开发期的云端 API 会收到助手读取的文件内容，以及照片的名称、拍摄时间、标签与相册名（照片画面不交给模型，见决定 6），这与相册界面“照片只在这台设备上分析，AI 不联网”的说明不一致（[ADR 0016](0016-ship-photo-ai-as-a-built-in-offline-capability.md)）。因此云端 API 只用于开发测试；本地多模态模型接入前，不在保存真实家庭数据的设备上为成员开启助手。
- Hermes 对个人空间里的文件直接 `patch` 会得到只读错误；系统随 Hermes 附带两个技能并在每个对话中自动加载：`anas-files` 说明目录、暂存区与“提交更改”，`anas-member` 由 Host Agent 按账号生成，写明这位成员的名字、发布位置与回收站。没有它们，真实模型要花十几轮探索才找到个人空间；有了它们，修改与删除 3–4 轮完成。Hermes 只从成员自己的 `config.yaml` 读取技能目录（不读 managed scope），所以这个文件由 root 写入、对成员只读；它不是安全边界，丢失只会让技能不加载。读取、搜索与编辑仍全部使用 Hermes 自带的工具。
- 助手目录是数据卷上每个账号一个 Btrfs 子卷（`assistant/<账号>`），以 simple quota（内核 6.7 起）封顶，每个账号 10 GiB（2026-10-16 用户决定）；文件代理因此可以从暂存区读取内容。数据卷离线时助手不可用，不回退到系统盘。在已有数据与快照的数据卷上开启 simple quota 前，须先在实验 NAS 上验证它对快照与删除的影响。
- 开发机上每个实例常驻约 200–270 MB（假模型）；用真实模型（DeepSeek）多轮对话后约 375 MB，峰值 403–442 MB（含 MCP 子进程）；冷启动 5.5–11 秒（实验 NAS 上到开始监听 4.4 秒，对话后约 400 MB）。登录即启动让每个登录着的、有助手的成员都占一个实例，不论这次是否使用；退出登录后实例照常闲置退出，没有登录的成员不占内存。运行环境解开约 425 MB（压缩包 132 MB），设备另需 Debian 包 `ripgrep`、`socat` 与 `tini`。本地多模态模型能否在 8 GB 设备上运行另行评估。
- Hermes 每开始一个新对话会多请求一次模型生成标题，正式配置须写明模型的上下文长度，否则它会反复探测；系统提示约 13,000 字符。
- 实例闲置退出后 Hermes 的定时任务不会触发，所以第一版关闭 `cronjob`；以后由 A-NAS 的调度唤醒实例。Hermes 的闲时整理（curator，归档久未使用的自建技能）同样等不到它要的 2 小时闲置，改由每周的 systemd 定时器在同一沙箱中运行 `hermes curator run`，实例运行时跳过；成员登录期间实例常驻，Hermes 自己的闲时整理也可能在实例中运行（[研究](../research/hermes-agent-runtime.md#后台复盘与闲时整理2026-10-16开发机)）。
- Hermes 的危险命令清单按命令文本匹配，挡得住失误（例如误删整个文件夹），挡不住刻意伪装的命令（`python -c` 调用删除）；个人空间与共享空间不被改动靠的是只读挂载与执行方，命令卡片只保护助手自己的目录与对话。
- Hermes 的 `memory` 与 `skill_manage` 会把内容留到以后的对话，这是诱导文字持续生效的唯一途径。边界测试中两个模型在对话里都没有把诱导写进去；但 Hermes 的后台复盘（用户决定保留）会在回合结束后自己写记忆与技能，测试中它把共享空间诱导文字的内容写进了记忆（以警示的形式），还自己建了技能（[研究](../research/hermes-agent-runtime.md#记忆与自建技能1142026-10-15开发机)）。对策：成员在“记忆”中能看到并删除这些内容，复盘改了什么也在这一轮下方显示；复盘只能用 Hermes 给它的工具（记忆、技能与只读的文件工具）：固定提交中这个限制没有生效，运行环境带上上游尚未合并的修复，直到 Hermes 升级到包含它的版本；回合结束后到达的审批也一律被产品服务拒绝。为了让复盘跑完，产品服务在回合结束后最多再保持连接 2 分钟（[研究](../research/hermes-agent-runtime.md#后台复盘与闲时整理2026-10-16开发机)）。
- Hermes 上游没有版本号，升级等同于一次依赖升级，需要重跑沙箱探针与契约测试。复制进前端的 Desktop 代码随同一提交更新：[`vendor-hermes-ui.py`](../../ai/assistant-spike/vendor-hermes-ui.py) 重新复制并改写导入，会牵连 Desktop 其余部分的四个模块由 A-NAS 的小替身代替；`@assistant-ui/tap` 必须与 Desktop 锁定的版本一致（现为 0.9.8），较新的 0.9.23 会让对话区陷入无限更新。
- 确认只在回合进行中有效：成员不在时，助手提交的更改在 `approvals.timeout`（1 天，2026-10-16 用户决定）后作废，要成员回来再说一次；成员的登录会话先结束时（浏览器登录 12 小时后过期），会话闸门切断连接，这一轮与卡片随之结束。换来的是卡片不会出现在别的对话中，助手当场知道结果，产品服务也不保存跨回合的待确认状态。Hermes 的审批请求不带工具参数，产品服务只把它对应到当前回合中进行中的那次“提交更改”（已有 `tool.start`、还没有 `tool.complete`、也还没对应过审批），回合结束（`message.complete`）后到达的审批一律拒绝：后台复盘调用“提交更改”时只发来审批请求，没有 `tool.start`。这依赖 Hermes 串行执行 MCP 调用，所以 A-NAS 的 MCP 服务器不声明并行调用。
- 离开对话、关闭窗口或刷新后回合继续：`hermes serve` 在客户端断开后保留回合，而实例只在套接字上有连接时存活，所以产品服务在这个成员还有回合在跑时保持一条到实例的连接，回合结束（`message.complete`）后再断开。会话闸门让这条连接也以登录为限：成员退出登录后它在 30 秒内被切断，实例约 45 秒后闲置退出，未完成的回合被打断。停止回答只有成员点“停止”（`session.interrupt`）一种。
- 删除账号时须同时删除其助手目录与 `Agent空间/<账号>`，随账号删除（[#26](https://github.com/zhongwater123/A-NAS/issues/26)）实现。
- Host Agent 新增类型化操作：为账号建立与删除助手目录、Agent空间子目录与实例套接字；文件代理新增“连接本人的助手”，并执行助手的更改：生成卡片、登记与查看凭本人会话，执行在只绑定进沙箱的助手套接字上按对端 UID 认人，由 Landlock 限制的工作进程完成。Host Agent 停止时切断它交出的全部助手连接，窗口自动重连；后台的回合如果在实例闲置退出前没有连接接上，就会被打断。

## 未选择

- **装进应用中心现有的 Docker**：安装策略不允许挂载个人空间；即使允许，Docker 默认给容器 `CAP_DAC_OVERRIDE`，Hermes 官方容器加固也保留它，容器内的 root 会无视 ACL。
- **每个账号一个独立 Docker 容器**：隔离强度与 systemd 沙箱相当，但依赖由管理员另装的 Docker、要扩展容器代理、镜像要另走离线交付，现有系统测试也不能直接证明它的边界。
- **直接使用 Hermes 自带的网页控制台（`hermes dashboard`）作为助手页面**：它是整台机器的管理台，配置、密钥、模型、插件等页面正是要固定住的部分，且可以切换机器上所有 profile；对话页是在伪终端里运行的终端界面，需要 Node.js 并为每个对话另起进程；确认卡片只能由成员本人在 A-NAS 会话中发出，控制台里做不到。
- **直接使用 Hermes Desktop**：它是 Electron 应用，带设置、模型、Profiles 与插件等页面，并假定客户端能调用 `hermes serve` 的全部接口，其中包括执行命令、改配置与新建 profile。A-NAS 只复用它的聊天层与 JSON-RPC 客户端（决定 9）。
- **一个进程服务多个 profile**：官方明说 profile 不是沙箱，成员之间的隔离只能依赖 Hermes 的代码。
- **以独立 UID 运行、所有读写都经 A-NAS 自写的 MCP 工具**：不需要成员 UID，但要重写读取、搜索与编辑工具，重复造轮子；读取范围已由挂载与 ACL 限定，同 UID 的风险已由沙箱封住。
- **overlayfs 让 Hermes 原地修改个人空间**：对工具最透明，但成员同时在使用的个人空间就是下层，内核文档把下层在挂载期间变化定义为未定义行为；挂载与清理暂存层还需要特权与卸载。
- **持久保存、过后在汇总中确认的待确认更改**（2026-10-14 原型的做法）：卡片要靠参数对应到提交它的对话，原型中曾“穿透”到其他对话；助手提交后回合就结束，不知道结果；产品服务要保存跨回合的状态并另定过期规则。
- **由 MCP 服务器在调用中发起 elicitation 来确认**：卡片文字与结果都由 A-NAS 决定，能直接对上更改，但等待发生在 Hermes 对该服务器的 RPC 锁之内，成员考虑期间同一实例所有对话的 A-NAS 工具调用都要排队。
- **产品服务直接持有每个成员实例的通道**（#111 时的做法）：实现最简单，但产品服务被攻破时可以在成员不在时指挥任何成员的助手，读到这个人的文件与照片元数据，并替他登记授权，破坏 ADR 0008 与 ADR 0011 “只能经正在登录的会话”的前提。
- **每个实例一个闸门进程代替 `systemd-socket-proxyd`**：闸门要有自己的系统身份、一个新的会话查询套接字，并自己实现复查与闲置退出；文件代理已经有会话查询、以 root 连接的能力和管理员终端的复查，复用它更少新增特权部件。
- **写个人空间或 Agent空间不需要确认**：共享空间任何成员都能写，可以放入诱导助手的文字；不确认就可能被诱导把私人文件写到全家可读的位置，或改坏本人的文件。
