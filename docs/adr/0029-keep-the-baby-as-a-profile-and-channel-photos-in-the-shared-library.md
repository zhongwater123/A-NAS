# 0029：宝宝是档案而不是账号，频道照片存入共享图库，记录由家庭服务持有

状态：proposed（2026-10-29 起草，尚未实现）

家庭中心第一版做宝宝频道（[规格](../specs/family-center.md)），这带来三个难以逆转的选择：

- 宝宝不会登录，但这份记录日后要由孩子自己的账号继承；
- 频道里的照片视频应当和家里其他照片放在一起；
- 成长、疫苗、日志与录音是家里最不能丢的数据。

我们决定：宝宝是家庭中心里的档案，不是账号；照片视频存入共享图库，频道只记录照片资产 ID；其余记录由以专用身份运行的家庭服务保存在数据卷上。

## 决定

1. **宝宝是档案，不是账号**：
   - 宝宝档案由家庭服务持有，带稳定 ID、姓名、性别、出生日与头像。它没有 Linux UID、个人空间、私有图库、Samba 凭据或 AI 助手实例。
   - 孩子长大后，管理员照常为他创建普通账号，账号认领档案。认领关系记在家庭服务中。
   - 档案 ID 保持不变，频道中的记录不需要迁移。认领时，档案的姓名成为账号昵称（与已有昵称冲突时请孩子另选），档案头像成为账号头像。
2. **家人关系只存在于家庭服务中**：家人、家庭角色、家长与亲友都是家庭服务里的记录，不对应 Linux 组或 ACL 条目，因为没有哪个文件或文件夹需要它们。GID 20002–20099 继续保留给以后的固定组（[ADR 0008](0008-use-unified-linux-identities-and-filesystem-acls.md)）。
3. **照片视频存入共享图库**：
   - 在频道里上传时，浏览器以上传者本人的会话，经相册服务的现有导入接口把照片视频存入共享图库。家庭服务只记录宝宝、照片资产 ID、添加者与添加时间。
   - 相册服务仍是照片资产的唯一权威：家庭服务不保存原图、缩略图或照片元数据的副本，每次读取照片都由相册服务按看的人做 Policy 检查。
   - 家庭服务列出频道照片时，以请求者的会话向相册服务批量查询这些照片资产的当前状态。因此在相册应用里移到回收站、恢复或永久删除，都会反映到频道中。
   - 由此带来的结果：所有账号都能在共享图库里看到这些照片，加入家庭只决定能不能看到频道里的记录。这是用户 2026-10-29 的决定：NAS 的账号就是家人。
4. **记录由家庭服务持有**：
   - 家庭服务 `anas-family` 以专用身份 `a-nas-family`（固定 UID/GID 31002）运行，独占数据卷上的 `family` 存储，里面是家庭服务的 SQLite 与录音文件。
   - `family` 存储由 Host Agent 在数据卷就绪时创建，并在漂移时修复，与 `photos`、`shares` 相同。数据卷离线时家庭中心整体不可用，不在系统盘暂存。
   - `anas-api` 把 `/api/v1/family` 请求连同会话令牌转发给家庭服务。家庭服务经 Host Agent 的会话查询确认身份，再按家庭 Policy（是否家人、是否家长、是否作者）授权。设备管理员没有隐式访问权。
5. **隐藏是相册服务中的一条收紧规则，照片不移动**（M2；规则见[规格](../specs/family-center.md#隐藏)）：
   - 孩子隐藏频道里的内容时，家庭服务先核对两件事：这个账号已认领这份档案；这项内容可以隐藏（孩子自己从共享图库加进频道、上传者是别人的照片不能隐藏）。核对通过后，家庭服务自己隐藏记录。
   - 对于照片视频，家庭服务还要经一个只有它能连接的套接字（相册服务按对端 UID 31002 认出它）告诉相册服务：共享图库中这份内容只给账号 Y 看。
   - 相册服务把隐藏记在 Catalog 中，以共享图库与内容对象为键，所以内容完全相同的照片资产，包括以后再传进来的，都一起隐藏。
   - 相册服务把它作为 [`internal/photos/policy.go`](../../internal/photos/policy.go) 中 `assetRules` 的一条规则执行。列表、单张读取、排序命中的复核、计数与错误信息都经过同一条规则。规则接口要扩展成能拿到看的人是谁，因为现有的“助手看不到视频”只看身份类型。
   - 这条路径只能让照片对更多人不可见，不能让任何账号多看到一张照片。孩子本人本来就能看到共享图库。
   - 设备管理员经[管理员查看模式](0008-use-unified-linux-identities-and-filesystem-acls.md)查看隐藏内容。这是查看授权的第三种范围（另两种是个人空间与私有图库），由 Host Agent 持有，经会话查询交给相册服务与家庭服务，两者都按它放行只读查看。

## 后果

- **多一个服务**：新增 `anas-family` 服务、`a-nas-family` 身份、systemd 单元与 `family` 存储。安装器、`make ops-check` 与系统测试要同步更新。播放浏览器不支持的录音格式时，家庭服务需要能连接 [FFmpeg Worker](../../CONTEXT.md) 的套接字，只传只读描述符。
- **被攻破时的影响**：
  - 产品服务被攻破时，只能以已登录的会话操作家庭记录，与相册的威胁模型相同；在 [#98](https://github.com/zhongwater123/A-NAS/issues/98) E01 落地前，产品服务仍能签发会话，这一缺口对所有服务都一样。
  - 家庭服务被攻破时，会暴露家庭记录与录音，但它只持有照片资产 ID，拿不到个人空间、共享文件夹或任何照片。
- **跨服务一致性**：频道可能引用已被永久删除的照片资产。家庭服务在相册服务报告“不存在”时删掉这条引用，不预先同步。相册服务要新增一个接口：按 ID 批量查询请求者能看到的照片资产及其拍摄时间与回收站状态。
- **备份**：`family` 存储的快照就是家庭记录的一致备份点，照片随相册的备份一起保存。只恢复其中一方时，会出现频道引用的照片不在，或照片还在共享图库、却不在频道里的情况；两者都不会丢掉照片本身。
- **隐藏覆盖每一条读取路径**：相册服务新增读取接口时，必须经过 `assetRules`。现有接口中，重复提示（[`internal/photos/hints.go`](../../internal/photos/hints.go)）等没有经过它的路径要逐一核对。系统用一个遍历全部读取接口的测试守住这一点。
- **隐藏管不到别人自己保存的东西**：别人私有图库里的同一张照片、已下载的副本、重新编码过的版本都不受影响。这是有意的：私有图库属于它的主人。

## 未选择

- **给宝宝建一个禁止登录的账号**：继承看起来最直接，但账号会带来 UID、个人空间、私有图库、Samba 凭据和 AI 助手实例。这些东西多年无人使用，管理员要看还得走审计查看模式。它还会出现在成员分享的收件人、用户列表等所有列出账号的地方，并牵扯账号删除与改密流程。
- **家庭图库（只对家人可见的第三种受管图库）**：频道照片与其他账号隔离，但要让相册服务认识家人关系。用户决定照片进入共享图库，因为 NAS 的账号就是家人。
- **把频道照片做成相册服务里的一种“宝宝相册”**：共享图库中的相册只有创建者和管理员能修改，不符合“家人都能添加、家长能移除”。要支持这一点，相册服务就得知道家庭角色。把这层引用留在家庭服务里，家庭规则就只在一处。隐藏照片仍需要相册服务配合（决定 5），但只是一条收紧的规则。
- **作为产品服务的模块**：
  - 记录放在系统盘上：会随系统盘一起丢失，也不在数据卷的快照里（理由同 [ADR 0011](0011-run-the-photo-library-as-a-dedicated-service-identity.md) 决定 2）。
  - 记录放在数据卷上一个属于 `a-nas` 的目录里：这正是 ADR 0011 否决的模型。
- **放进相册服务**：相册服务会持有与照片无关的成长和疫苗记录，被攻破时影响面更大。家庭中心以后还会有其他家人的频道，是独立的领域。
- **隐藏时把照片挪进孩子的私有图库**：完全复用私有图库的现有规则，但它是“拿走”而不是“隐藏”。挪回来的是一个新的照片资产，原来的相册、标签和上传者都丢了；别人再传一遍同一张照片，它又会出现。而且从共享图库移走别人上传的照片，原本只有上传者和管理员能做，这会让家庭服务得到比收紧可见范围更大的权限。
- **家人做成 Linux 组，记录放在一个按组授权的共享文件夹里**：SMB、终端与应用都能绕过“作者才能改、家长才能删”的规则，而 ACL 只到共享文件夹根目录，无法表达这些规则。
