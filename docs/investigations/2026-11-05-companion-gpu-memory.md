# 电脑桌宠静置时 GPU 进程占内存的来源

状态：open
更新时间：2026-11-05

## 症状与影响

电脑桌宠紧凑静置、只显示过待机动画时，Electron 全部进程的私有内存合计 243–246 MB，其中 GPU 进程 131–134 MB，已经贴近 [ADR 0033](../adr/0033-run-the-desktop-companion-in-an-electron-shell.md) 的 250 MB 提示线。拖动过、专注到点过之后静置，合计升到 298 MB。常驻程序一直占着这些内存。

## 最小复现

1. Windows 11，Intel Core Ultra 5 225U 集显（没有独显，“专用 GPU 内存”恒为 0），单屏，150% 缩放；Electron 45.2.3。
2. 离线模式启动桌宠，就绪后不碰它，静置 5 分钟。
3. 用 `app.getAppMetrics()` 取各进程私有内存与这 5 分钟的平均 CPU；GPU 进程的共享显存取自性能计数器 `\GPU Process Memory(pid_*)\Shared Usage`；记下这期间页面上 `data-action` 出现过的姿势。
4. 每个变体单独启动一次，改动只做在临时副本里。

## 观察事实

渲染后端：Skia GaneshGL 经 ANGLE 走 Direct3D 11，合成与光栅化都是硬件加速，Graphite 关闭。同一配置干净地测了三次：GPU 131–134 MB、合计 243–246 MB、CPU 0.51–0.71%，这就是噪声范围。

| 变体 | 改动 | GPU 私有 | 页面私有 | 合计私有 | 共享显存 | CPU % |
|---|---|---|---|---|---|---|
| 基线 | 只显示过待机（三次中的一次） | 131.0 | 47.6 | 243.3 | 54.4 | 0.51 |
| 动画停 | 页面按“减少动态效果”渲染，精灵动画为 none | 101.0 | 44.0 | 207.8 | 11.2 | 0.06 |
| 关硬件加速 | `app.disableHardwareAcceleration()` | 16.6 | 49.8 | 132.6 | 0 | 0.55 |
| 隐藏 | 就绪后 `pet.hide()` | 133.3 | 40.5 | 238.2 | 69.8 | 0.31 |
| 互动后 | 拖动一次、专注 1 分钟到点，再静置 | 180.1 | 54.2 | 298.0 | 79.5 | 0.70 |
| 小窝开着 | 打开小窝静置 | 169.3 | 96.5（两个页面） | 333.8 | 89.6 | — |
| 关小窝 1 分钟后 | 小窝窗口被销毁 | 147.3 | 47.6 | 262.8 | 66.6 | 0.49 |
| 遮挡计算开关 | `CalculateNativeWinOcclusion` | 167.0 | 50.9 | 281.6 | 99.3 | 0.97 |
| 去掉每秒重渲染之后 | 提交 6588c39c（UI-2） | 130.8 | 45.3 | 243.1 | 54.4 | 0.70 |

另有三组（不预加载、不透明窗口、关闭 GPU 光栅化）在静置期间被真实鼠标拖过，多显示了两个姿势，数字不能直接比，不据此下结论。网络进程恒定约 18 MB，计入合计。

## 假设

- 精灵帧图解码后的纹理是 GPU 的大头：只对一部分。动画停下时 GPU 仍有 101 MB。
- 透明窗口的合成开销是大头：没看到。不透明那组在噪声内（该组被拖过，结论弱）。
- 预加载其余帧图会占 GPU：没看到。基线开着预加载、只显示过待机，仍是 131 MB；预加载只下载、不上传，画出来时才占（推断）。
- 每秒一次的 React 重渲染占 CPU：测不出。空闲 CPU 几乎都花在精灵动画上。

## 根因

1. **约 100 MB 是开着硬件加速就有的固定开销**（ANGLE/D3D11、驱动与 Skia 的 GL 上下文），与页面画什么关系不大：动画停 101 MB，关硬件加速 17 MB。
2. **精灵动画再加约 30 MB 私有、约 43 MB 共享显存和几乎全部空闲 CPU**：`background-position` 逐帧动画每帧都要重绘（[`companion.module.css`](../../web/src/companion/companion.module.css) 的 `.petSprite`）。
3. **每显示过一个新姿势，它的整条帧图就留在 GPU 上**：互动后比基线多 49 MB，回到待机也不释放（[`Character.tsx`](../../web/src/companion/Character.tsx) 每个姿势一条 13440 px 宽的帧图）。
4. 关掉小窝后页面进程归还约 49 MB，GPU 一分钟内只还一部分，比基线多约 16 MB。

## 修复与回归证据

已做两项，等复测：

- **待机一分钟后静止**（对应根因 2）：待机动画播 6 遍（一分钟）后停在第一帧，直到再被要求换姿势；任务进行中的姿势照常循环。见 [`Character.tsx`](../../web/src/companion/Character.tsx) 的 `IDLE_LOOPS`。按“动画停”一组，预计静置时省约 30 MB GPU 和九成以上空闲 CPU。
- **给 GPU 图片缓存设上限**（对应根因 3）：页面里换下的姿势已经从 DOM 移除，留着帧图的是 GPU 进程的图片缓存，页面自己清不掉。[`main.cjs`](../../desktop/companion/main.cjs) 加了 Chromium 开关 `force-gpu-mem-discardable-limit-mb=32`，超过 32 MB 时丢掉没在画的帧图。这一项是推断：多出的 49 MB 里有多少是帧图还不知道（拖动和到点提醒也会占）；上限压得比同时在画的帧图还低，可能每帧都要重新解码。

复测按上面的方法，在同一台机器上测：

1. 只显示过待机，静置 5 分钟（与基线比）。
2. 互动后静置（与“互动后”一组比），各测一次带开关和不带开关的，分出两项各自的效果。
3. 小窝开着、桌宠和小窝里的大肥鱼都在动的时候测 CPU，确认 32 MB 不会让帧图反复解码。

没有收益或有副作用的那一项就撤掉。另补测 macOS。

其他方向：

- 关硬件加速：这台机器上内存和 CPU 都更省（合计 133 MB），但渲染全落到 CPU，小窝窗口的流畅度、弱 CPU 机器和 macOS 都没测。
- 两个 Chromium 开关不值得：关闭 GPU 光栅化 CPU 升到 1.18%，遮挡计算没有改善。

## 后续工作

- 按上面的三项复测，结果填进观察事实的表格，再决定两项修复的去留；需要的话把不预加载、不透明窗口两组干净地重测。
- macOS 上按同样方法测一次基线，作为 ADR 0033 的 macOS 参考。
