# 每次列目录对账整个空间，大空间下列目录与影视扫描以十秒计

状态：fixed locally（未部署）
更新时间：2026-10-21

## 症状与影响

[#167](https://github.com/zhongwater123/A-NAS/issues/167)（架构审查 [#159](https://github.com/zhongwater123/A-NAS/issues/159)，基线 `9cda8a3`，P1）。审查只读源码，未在实验 NAS 上测量。2026-10-21 在 `8f5b6b0`（已含 #164 的排序修复与 #162 的快照修复）上逐条复核，五项都仍然存在：

1. `List` 与 `Tree` 每次都经文件代理扫描整个空间，再逐条登记：每个条目约 4 条语句（#164 之后在一个事务内，不再逐条自动提交），都占用 `files.db` 的单连接。点开一个文件夹的代价与整个空间的条目数成正比。
2. 影视中心对每个库文件夹各调一次 `Tree`，音乐对每位成员的每个音乐文件夹各调一次，每次都是整空间。打开的影视中心每 20 秒请求一次刷新：上次扫描结束超过 2 分钟的库被扫描，扫描进行中的库被要求“结束后再跑一次”，所以单次扫描超过 2 分钟的库在窗口打开期间一直在扫描。
3. 文件代理单条消息上限 64 MiB。约 30–40 万条目的空间扫描结果超过它时，工作进程写出失败并退出，代理返回 `unavailable`，之后每次列目录都启动新进程重扫，这个空间永远列不出来；没超过时 root 进程也要整体解码再编码一次。
4. 代理以 `context.Background()` 执行，每个账号只有一个工作进程且整个操作持锁：成员复制或删除大文件夹期间，他的其他网页操作全部排队，关闭浏览器也不会停止。
5. `files.db` 的审计表没有索引；活动记录按 `strftime(occurred_at)` 排序和翻页，`accounts.db` 已有的索引用不上，每页都要算出整张表的时间再排序。快照在一个事务中逐对象插入。

## 最小复现

[`TestReconcileAtScale`](../../internal/files/reconcile_scale_test.go) 在临时卷上建出约 10 万个条目（`库/` 下 1,100 个文件夹与 9.8 万个文件，`小/` 20 个文件，`影视/` 10 个文件夹共 1,000 个文件），用记录扫描的文件系统与 `entries` 上的触发器统计每一步的扫描条目数与写入行数：

```sh
ANAS_SCALE_ENTRIES=100000 go test ./internal/files/ -run AtScale -v
```

WSL ext4，同一台开发机先后两轮（负载 3–11，耗时受负载影响明显，条目数与写入行数是确定的）：

| 步骤 | `8f5b6b0` 耗时 | 修复后耗时 | 扫描条目 前 → 后 | 写入行 前 → 后 |
|---|---|---|---|---|
| 整空间，首次 | 13.2 / 34.1 s | 22.8 / 9.2 s | 99,133 → 99,133 | 99,133 → 99,133 |
| 整空间，无变化 | 14.4 / 18.8 s | 0.91 / 0.63 s | 99,133 → 99,133 | 99,133 → 0 |
| 列根目录 | 10.3 / 22.5 s | 0.4 / 0.3 ms | 99,133 → 3 | 99,133 → 0 |
| 列 `小/`（20 个文件） | 25.1 / 33.5 s | 0.3 / 0.8 ms | 99,133 → 20 | 99,133 → 0 |
| `Tree(影视)`（1,010 个条目，影视扫描读取的方式） | 35.7 / 14.5 s | 6.8 / 5.7 ms | 99,133 → 1,010 | 99,133 → 0 |
| 拍快照（只计目录写入，后端列出现有空间） | 2.6 / 2.5 s | 1.7 / 0.9 s | — | — |

基线每次列目录都把 99,133 行全部重写一遍，并且随 WAL 增长越来越慢。首次整空间对账两轮结果互有快慢，属负载波动：每个新条目的语句数没有变化。

## 观察事实

- `List`、`Tree`、快照比较与“最近删除”都调用同一个整空间 `reconcile`；后台每 5 分钟对每个记住的会话可见的每个空间再做一遍，共享空间按成员数重复。
- 登记的 upsert 不比较现有行，未变化的条目照样写；`files.db` 只有一个连接，事务期间其他请求等待。
- 代理的扫描应答是一条 JSON 消息；`writeMessage` 超限时返回错误，`serveWorker` 随即退出。
- `RefreshStale` 以上次扫描结束时间判断陈旧，但不看扫描是否正在进行；`scan` 拿不到锁时置 `again`。
- `activity.Table.List` 的子查询把 `strftime(...)` 作为 `at` 排序；`EXPLAIN QUERY PLAN` 为全表扫描加 `USE TEMP B-TREE FOR ORDER BY`。

## 假设

| 假设 | 验证方法 | 结果 |
|---|---|---|
| 列目录的代价与空间大小成正比 | 10 万条目上测列 20 个文件的文件夹 | confirmed：25–34 s，扫描与写入都是 99,133 |
| 只对账列出的文件夹会丢掉经 SMB 移动的条目 ID | 先列移出的文件夹、再列移入的文件夹 | ruled out（修复后）：部分对账不删行而是待定，移入处按 inode 放回原 ID |
| 文件夹经 SMB 改名后其下各行要等逐层列出才可打开 | 改名后直接打开其下文件 | ruled out（修复后）：改名的行带着其下各行一起改写路径 |
| 部分对账的写入会让同时进行的整空间对账永远被丢弃 | 整空间扫描暂停期间反复列一个未变化的文件夹 | confirmed（修复中途发现）：改为只有改了行的写入才推进代次 |
| 影视刷新在扫描进行中追加一次扫描 | 扫描暂停期间刷新 5 次 | confirmed：文件夹被读 2 次，修复后 1 次 |
| 待定的行会被复用了其 inode 号的新文件接管（CI 发现） | 上传把文件改名就位时，把已删文件的待定行改成新文件的 inode | confirmed：新文件拿到已删文件的 ID；修复后新建的对象先删掉持有其 inode 的行 |

## 根因

对账没有范围：任何需要“这里是最新的”的读取都对整个空间做一次扫描与全量写入，写入又不区分有没有变化。影视与音乐按文件夹调用，把这一代价再乘以文件夹数；刷新逻辑把“扫描中”当作“陈旧”，长扫描因此首尾相接。文件代理把扫描当作一条消息、把一条消息的失败当作进程的失败，并且按账号串行、不传递取消。

## 修复与回归证据

- 按范围对账（[reconcile.go](../../internal/files/reconcile.go)）：`List` 只浅扫描该文件夹的子项，`Tree` 只扫描该子树；写入与范围内现有行逐项比较，只写有变化的行。只有整空间对账删除没找到的行；部分对账把它们改到 `.a-nas-stale/<id>` 待定，列表与重名检查不包含，之后任何对账在别处找到同一 inode 就以原 ID 放回。文件夹改名或移动时其下各行随它改写路径，经它的待定路径中转以免中途撞上 `UNIQUE(space_id, relative_path)`；同名位置被另一个文件夹占用时，旧文件夹下的行随旧行待定。文件夹不在记录位置时 `List`/`Tree` 改做一次整空间对账再找。
- A-NAS 刚建出的对象（新建文件夹、上传、文件夹上传、复制）先删掉持有其 inode 的行再登记：inode 是新的，持有它的行属于已不存在、号码被重新分配的文件（ext4 会立即复用，CI 上已删文件的待定行被上传的新文件接管）；文件与文件夹之间换了类型的行也不复用。
- 整空间对账（后台、快照比较、“最近删除”、`Tree` 整空间、上述查找）每个空间一次只跑一个，等待者由开始于其请求之后的一次满足；后台循环跳过 4 分钟内对账过的空间。一行也没改的写入不推进代次（[ordering.go](../../internal/files/ordering.go)），浏览不再丢弃长时间的整空间对账。
- 影视刷新跳过正在扫描或等待扫描的库（[scan.go](../../internal/media/scan.go)）；网页变更仍会要求结束后再扫一次。
- 文件代理（[server.go](../../internal/filebroker/server.go)、[worker.go](../../internal/filebroker/worker.go)、[wire.go](../../internal/filebroker/wire.go)）：扫描按每页最多 2048 个条目分页，代理逐页转发；超过 64 MiB 的应答改为错误应答，工作进程继续服务；Product Service 关闭连接时代理向工作进程发送取消，工作进程停止当前操作并应答；每个账号最多 4 个工作进程。大文件复制每 64 MiB 检查一次取消（[rootfs_linux.go](../../internal/files/rootfs_linux.go)），`io.CopyN` 保留 `copy_file_range`。
- 活动记录：`accounts.db`、`files.db`、`storage.db` 为排序所用的表达式与 ID 建索引（[activity.go](../../internal/activity/activity.go) 的 `IndexStatement`），按游标、类别或文字翻页都沿索引读取。
- 测试：
  - [reconcile_scope_test.go](../../internal/files/reconcile_scope_test.go)：列目录只扫描并写该文件夹、未变化时零写入；文件夹经 SMB 改名后其下文件不经整空间对账即可打开；文件经 SMB 移动先列移出处仍保留 ID；直接打开被移走的文件夹只做一次整空间对账；先列移出处、再列移入处后整个子树跟随；同名替换的新旧文件夹各自保留；经 SMB 删除的文件立即不列出、不占名字，整空间对账后行删除；新上传的文件即使拿到已删文件的 inode 号也不接管其 ID；`Tree` 只扫描子树并只写变化的 2 行；整空间扫描期间列未变化的文件夹不丢弃它；4 个并发整空间请求只扫描 2 次，后台循环随后跳过。
  - 已有的 [reconcile_race_test.go](../../internal/files/reconcile_race_test.go) 全部通过，后台反复对账时删除与恢复的用例加入了整空间 `Tree`。
  - [影视刷新测试](../../internal/media/service_test.go)（`TestRefreshLeavesAScanInProgressAlone`）：修复前文件夹被读 2 次。
  - [worker_test.go](../../internal/filebroker/worker_test.go)：分页、超限应答后同一进程继续服务、取消扫描与复制、长操作不挡同账号的其他调用、池满时排队或随调用方放弃、回收只停空闲进程。
  - [index_test.go](../../internal/activity/index_test.go)：四种翻页方式的查询计划都使用 `audit_events_at` 且不排序；去掉索引则失败。
  - `go test -race` 覆盖 `internal/files`（3 轮）、`filebroker`、`assistantchanges`、`sharefiles`、`media`、`music`。

## 未照 issue 做的项与原因

- **按目录 mtime/ctime 跳过子树**：文件原地改写（Windows 经 SMB 覆盖同名文件、音乐标签编辑）只改文件自身的时间与大小，不改目录的 mtime，按目录跳过会让这些修改一直进不了目录。逐项比较之后，未变化的子树只剩一次遍历与一次读取，零写入；10 万条目的整空间无变化对账 0.6–0.9 s。
- **`RefreshStale` 以扫描开始时间判断陈旧**：单次扫描超过 2 分钟时，开始时间在扫描结束时已超过 2 分钟，下一次立即开始，仍然首尾相接。改为扫描中或等待中的库不再追加，陈旧仍以上次结束计，两次扫描之间至少隔 2 分钟。
- **审计保留规则**：[日志规格](../specs/logs.md)写明活动记录永久保存、不提供删除，改变需要产品决定，本次只建索引。
- **相册目录的审计索引**：`catalog.db` 使用带版本号的迁移，加索引要升版本并在部署回滚中处理，相册的审计量也小，留待下次有迁移时一起做。
- **快照分批插入**：条目经外键引用快照行，分多个事务写入就会让写到一半的快照可见，要加“就绪”标记并改约 7 处读取、清扫与启动时的补算。10 万条目的快照写入（含遍历）共 0.9–1.7 s，定时快照最多每小时一次，本次不做。

## 后续工作

- 部署：Host Agent 与 Product Service 同版本部署。新旧混用两个方向都安全（旧 Product Service 不请求分页，仍受 64 MiB 单条上限，但超限变为错误应答）。新增的只有 `audit_events_at` 索引（`IF NOT EXISTS`，回滚无需处理），没有表结构迁移。
- 实验 NAS 验收：在条目最多的空间上记录列根目录与深层文件夹的耗时；经 SMB 改名一个文件夹后在网页中打开其下文件；影视中心打开 10 分钟，确认没有连续扫描（Host Agent 日志中扫描请求的间隔）；一个成员复制大文件夹期间，同一成员列目录与预览不排队，关闭页面后复制停止。
