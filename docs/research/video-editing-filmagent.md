# FilmAgent：多智能体协作的虚拟影片制作

> 状态：完成（论文与开源代码精读；未在开发机复现）  
> 更新日期：2026-10-25  
> 适用范围：arXiv [2501.12909](https://arxiv.org/abs/2501.12909) v1（2025-01-22，作者标注 Work in progress），代码 [HITsz-TMG/FilmAgent](https://github.com/HITsz-TMG/FilmAgent) 的主干  
> 关联：[CutClaw 调研](video-editing-cutclaw.md)、[AI 助手规格](../specs/ai-assistant.md)、[相册视频规格](../specs/photo-video.md)

本文为“指令驱动剪辑”的剪辑计划生成做调研，重点看 FilmAgent 的多智能体协作能否提升计划质量。论文与代码不一致的地方以代码为准，并逐条注明。

## 基本信息

- **性质**：学术论文加开源实现，作者来自哈尔滨工业大学（深圳）与清华大学。代码使用 MIT 许可，约 1,900 星。
- **任务**：输入一句故事创意（例如“分手争吵的一场戏”），在预先搭好的 Unity 3D 场景里自动产出一段带对白、动作和运镜的短片。
- **与我们的关系**：它**生成**影片，不剪辑真实素材；不涉及视频理解、检索或定位。可借鉴的只有“计划怎么产生、怎么互相审校”这一层。
- **依赖的模型**：GPT-4o（`gpt-4o-2024-05-13`），对比组用 o1-preview（在 ChatGPT 网页上手工运行）；配音用 ChatTTS。

## （1）摘要

FilmAgent 让多个 LLM 智能体扮演剧组角色：导演、编剧、演员、摄影师。它们按真实剧组的流程分三个阶段协作：

1. 创意开发：确定人物与分场大纲；
2. 剧本写作：写对白，标注站位与动作；
3. 摄影：为每句台词选择镜头。

其中提出两种协作算法：**Critique-Correct-Verify**（批评、修改、验证，用于剧本）和 **Debate-Judge**（辩论、裁决，用于镜头）。

剧本定稿后在 3D 空间里自动拍摄。评测用 15 个创意和 4 项人工指标，平均 3.98/5，明显高于单智能体。用 GPT-4o 的多智能体版本还超过了用 o1 的单智能体。

## （2）关键流程

```
故事创意 + 3D 空间清单（15 个地点、65 个站位、21 种动作、9 类镜头）
  │
  ▼
① 创意开发（导演）
   生成人物档案（性别、职业、性格、说话风格）→ 分场大纲：每场写清 who / where / what
  │
  ▼
② 剧本写作
   a. 编剧写初稿：对白 + 每句台词的站位与动作（只能从动作清单里选）
   b. 导演 ↔ 编剧：Critique-Correct-Verify，最多 3 轮
      导演指出情节不连贯、动作不合理 → 编剧修改 → 导演验证是否改到位
   c. 演员 → 导演 → 编剧：演员按自己的人设对台词提意见，导演筛选汇总后，
      再与编剧走一次 Critique-Correct-Verify
   d. 标注移动（走位）
  │
  ▼
③ 摄影：Debate-Judge
   两方各自为每句台词选镜头 → 互相指出分歧并修改 → 导演裁决
  │
  ▼
④ 清洗剧本：把所有字段对齐到 3D 空间里实际存在的人物、地点、动作与镜头
  │
  ▼
⑤ ChatTTS 为每句台词配音，以音频长度决定该句的镜头与动作时长 → Unity 拍摄
```

最终产物是一份结构化的 JSON 剧本：每场有 `scene information`（who / where / what）和 `initial position`，每句台词有说话人、内容、动作、镜头和当前站位，走位单独记在 `move` 里。

## （3）核心方法

### 角色分工

| 角色 | 职责 | 对应剪辑场景的类比 |
|---|---|---|
| 导演 | 定人物与大纲、批评剧本、冲突时拍板 | 理解用户意图、定叙事结构、最终把关 |
| 编剧 | 写对白，标注站位与动作，按批评修改 | 写剪辑计划：每段用什么素材、多长、什么顺序 |
| 演员 | 检查台词是否符合自己的人设 | 检查计划是否忠于素材本身（素材里真有这个画面吗） |
| 摄影师 | 为每句台词选镜头 | 选转场、景别节奏、配乐 |

### 两种协作算法

**Critique-Correct-Verify**（论文算法 1）：

1. 执行方 P 根据上下文和指令生成结果 R；
2. 批评方 Q 写出改进意见 F；
3. P 吸收意见后修改 R；
4. Q 验证意见是否都已解决：解决了就停，否则继续，最多 M 轮（实验取 3）。

关键在于**验证步只核对上一轮的意见**，而不是重新挑一遍刺，这样能收敛。

**Debate-Judge**（论文算法 2）：两个同级智能体各自给出方案，几轮互评之后，由第三方裁决者综合讨论给出最终决定。适合没有唯一正确答案、需要权衡的主观选择。

### 封闭词表

模型可以选的地点、站位、动作和镜头，全部来自预先定义的清单，每项都附有人写的说明。例如站位 B 的说明是“沙发旁、可坐、在 A 与 C 之间，便于和这两个位置的人物交流”；镜头有使用准则（跟拍镜头只能在人物移动时使用）。所以协作要解决的是“在有限选项里选对”，而不是自由发挥。

### 代码与论文的差异

- **摄影阶段的参与者**：论文写两名摄影师辩论、导演裁决。代码（`stage3_verify`）是导演与摄影师各出一份镜头标注，最多 4 轮互相审阅并修改自己的版本，最后导演在两份里**二选一**，而不是综合两份。
- **验证是字符串匹配**：代码在验证者的回答里找 `finalize` 后面有没有 `True`，没有结构化输出。
- **真正防住幻觉的是最后的清洗**：`clean_script()` 用最相似匹配，把人物、地点、动作、镜头逐一对齐到清单里实际存在的项；`find_unknown_actions()` 专门找出清单之外的动作。也就是说，LLM 之间的讨论减少了错误，但最后还是靠确定性代码兜底。
- **规模被硬限制**：代码里人物最多 4 个、场景最多 3 场。

### 实验结论的可信度

| 方法 | 模型 | 动作准确率（0–1） | 情节连贯 | 人设一致 | 镜头恰当 | 平均（5 分制） |
|---|---|---|---|---|---|---|
| CoT 单智能体 | GPT-4o | 0.68 | 1.60 | 3.84 | 1.67 | 2.63 |
| CoT 单智能体 | o1 | 0.80 | 2.73 | 3.60 | 2.86 | 3.30 |
| FilmAgent 单人分阶段（Solo） | GPT-4o | 0.80 | 1.87 | 4.20 | 2.07 | 3.04 |
| FilmAgent 多智能体（Group） | GPT-4o | 0.88 | 3.53 | 4.44 | 3.53 | 3.98 |

- **分阶段本身有用**：Solo 比 CoT 高 0.41 分。**协作带来更大提升**：Group 比 Solo 高 0.94 分，主要来自情节连贯（+1.66）与镜头（+1.46）。
- **修改前后的人工偏好**：导演-编剧讨论后的剧本胜 66.7%、平 20%、负 13.3%；演员参与后胜 73.4%、平 13.3%、负 13.3%；镜头辩论后胜 44%、平 38%、负 18%。镜头这类主观选择，辩论的收益明显更小，而且近五分之一变差。
- **局限**：只有 15 个创意，全部人工评分；对比的是 2024 年的模型，换成更强的推理模型后，多智能体的优势会缩小多少，论文没有回答。作者自述的不足包括：标注粒度太粗（一句台词只配一个动作和一个镜头）；全程只看文字，没有用多模态模型核对画面；缺少剪辑、配乐、调色等角色。

## （4）对 A-NAS 的借鉴与创新思考

### 定位

FilmAgent 解决的是“从一个想法生成一份可执行的结构化脚本”，这正对应我们剪辑计划生成这一步。它不能帮我们找素材，找素材要靠 [CutClaw](video-editing-cutclaw.md) 的分层定位和 Gallery 的窗口向量。

### 可以直接借鉴的

1. **先分阶段，再谈协作**：Solo 已经明显优于一步到位的 CoT。剪辑计划可以拆成三步：意图解析（时长、主题、人物、时间范围、风格）→ 叙事大纲（分几段，每段讲什么、多长）→ 逐段选片。每一步的输出都是可校验的结构化数据。
2. **封闭词表加确定性清洗**：这是 FilmAgent 最值得学的工程点。我们的剪辑计划只能引用真实存在的照片资产 ID 与合法时间段，转场、景别、配乐只能从清单里选。LLM 输出之后先由代码对齐和校验，引用不存在的素材、越界或重叠就直接拒绝，并给出结构化原因。
3. **Critique-Correct-Verify 用在叙事层**：一方写剪辑大纲，另一方对照用户指令和候选素材的描述挑问题（漏了指令里的人物、时间顺序乱了、某段素材明显不够用），修改后只核对上一轮的意见，最多 3 轮。
4. **“演员”视角对应“素材是否支持”**：FilmAgent 让演员按人设检查台词；剪辑里可以让一个检查方只看候选素材的描述或缩略图，判断计划里每段描述在素材中是否真有对应。这能防住“计划写得很美，但图库里根本没有这个画面”的幻觉。
5. **时长由外部信号决定**：FilmAgent 用配音长度决定镜头时长，CutClaw 用音乐节拍，思路一致。我们的剪辑计划也应由配乐节拍或用户给的总时长来约束每段长度。

### 需要谨慎的

- **辩论对主观选择收益有限**：镜头辩论只赢 44%、输 18%。转场、配乐这类主观选择，不值得花多轮 LLM 调用去辩论；用规则默认值，或者交给用户在预览中调整，更划算。
- **成本与隐私**：一次完整的 FilmAgent 要调用几十次 GPT-4o。在 A-NAS 上，本地模型接入之前只能用云端模型做开发测试（见 [AI 助手规格](../specs/ai-assistant.md)），协作轮数必须有硬上限，并且只把素材的文字描述而不是原图发给模型。
- **结论可能过时**：用 o1 级别以上的推理模型，单智能体加明确分阶段，可能已经足够。要先在我们自己的指令集上比较“单模型分阶段”与“加一轮批评”，再决定要不要多智能体。

### 创新点

1. **客观约束交给代码，主观判断才交给 LLM**：FilmAgent 让导演用 LLM 去查情节和动作错误，最后又靠代码清洗兜底。我们反过来设计：时长、重叠、引用合法、覆盖指令里的人物和时间，这些都由校验器直接判定并生成批评意见；LLM 批评方只负责叙事是否通顺、节奏是否合适。
2. **用户是最终的导演**：FilmAgent 的导演是模型。A-NAS 的剪辑计划在渲染前交给用户确认，用户的修改（换一段、删一段、调顺序）作为新一轮“批评”输入，复用 Critique-Correct-Verify 的结构。
3. **多模态验证补上 FilmAgent 的短板**：它只看文字。我们的检查方可以拿到候选片段的关键帧缩略图，以及向量相似度分数，用来核对“描述与画面是否一致”。
4. **与 VNAS 助手结合**：剪辑计划的生成、修改、确认可以作为 VNAS 的一项技能。助手负责对话和计划编辑，相册服务负责校验与检索，媒体 Worker 负责渲染。这与助手“改动前先经本人确认”的规则一致。

### 待验证

- 在 20–30 条真实中文剪辑指令上，比较单模型直出、单模型分阶段、分阶段加一轮批评这三种方式的剪辑计划质量与调用成本。
- 校验器能拦下多少类错误，剩下哪些只能靠 LLM 或用户发现。
