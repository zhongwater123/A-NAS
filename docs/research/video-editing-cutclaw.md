# CutClaw：音乐同步的长视频智能剪辑

> 状态：完成（论文与开源代码精读；未在开发机复现）  
> 更新日期：2026-10-26  
> 适用范围：arXiv [2603.29664](https://arxiv.org/abs/2603.29664) v1（2026-03-31），代码 [GVCLab/CutClaw](https://github.com/GVCLab/CutClaw) 2026-04-17 的主干  
> 关联：[FilmAgent 调研](video-editing-filmagent.md)、[相册本地 AI](../architecture/photo-ai.md)、[相册视频规格](../specs/photo-video.md)

本文为“用户给一句指令，检索相关照片与视频片段并剪成成片”的需求做调研，重点看 CutClaw 的抽帧方式与片段定位。论文与代码不一致的地方以代码为准，并逐条注明。

## 基本信息

- **性质**：学术论文加开源实现，作者来自大湾区大学 GVC Lab、北京交通大学与腾讯 ARC Lab。代码约 990 星，仓库**没有声明许可证**，所以只能借鉴思路，不能复制代码。
- **任务**：输入一段 1–3 小时的原始素材（电影或 Vlog）、一首音乐和一句文字指令，输出一段 20 秒到 1 分钟、剪辑点与音乐节拍对齐的短视频。
- **依赖的模型**：全部是大模型，需要云端 API 或 GPU。
  - 镜头描述：Qwen3-VL-30B-A3B；音乐描述：Qwen3-Omni-30B-A3B；
  - 规划：Gemini 3 Pro；选片与审片：MiniMax-M2.1；
  - 语音转写：Whisper-v3-turbo，加 pyannote 说话人分离；
  - 镜头检测：PySceneDetect；节拍检测：madmom。

## （1）摘要

CutClaw 把“从长素材剪出短片”写成一个联合优化问题：在原素材上选出一串片段 `(入点, 出点)`，同时最大化四项指标：画面质量、叙事连贯、对指令的忠实度、剪辑点与音乐的同步。

整个解空间太大，没法直接搜索，所以它按“自底向上拆解、自顶向下定位”分层剪枝：

1. 先把视频拆成镜头，再聚合成场景；把音乐拆成段落和关键节拍点。
2. Playwriter（编剧）以音乐结构为时间骨架，把场景分配给各个音乐段落，再为每个节拍区间写出一条镜头规格。
3. Editor（剪辑师）在指定场景的附近找出符合时长的片段。
4. Reviewer（审片）对每个候选做拒绝采样，不合格就打回 Editor 重选。

论文自建了 10 组素材（5 部电影、5 段 Vlog，共约 24 小时），每组配两类指令，共 20 个测试用例。结果在画面质量、指令跟随和音画同步三项上都超过 NarratoAI、UVCOM 和 Time-R1；25 人共 2,000 票的用户研究中，各项得票率都在 45%–58%。

## （2）关键流程

```
原始视频 ──► 采样：2 fps、短边 240 px（论文写 360p），供镜头描述使用
  │            PySceneDetect AdaptiveDetector 另读原片、跳帧到约 2 fps 切镜头
  │            Whisper 转写 + 说话人分离 → 推断人物名单 H
  ▼
逐镜头描述（Qwen3-VL）：超过 30 s 的长镜头切成子片段，帧与字幕一起送入
  │  输出结构化属性：地点类型、时间状态、环境标签、光线/色调、景别、叙事功能、事件摘要、情绪
  ▼
镜头 → 场景聚合：相邻镜头加权相似度 < 0.5 就切开（细节见下一节）
  │  场景超过 300 s 就拆开；短于 30 s 的并入相邻场景
  ▼
音乐 ──► madmom：重拍、音高变化、频谱能量变化 → 去重合并成候选切点
  │      Qwen3-Omni 划分主歌/副歌等段落 → 按强度为切点打分，保留重要切点
  ▼
Playwriter（Gemini 3 Pro）
  ① 场景分配：每个音乐段落分到一组场景，各段之间不得重复，违反就带上负面约束重新生成
  ② 镜头规划：段落内每个节拍区间产生一条规格 p = (目标时长 τ, 场景 ID, 画面描述 d)
  ▼
Editor（MiniMax-M2.1，ReAct 循环；4 个镜头并行，冲突时重跑，最多 2 次）
  工具一：语义邻域检索：读取推荐场景（可扩到前后 ±3 个场景）里各镜头的文字描述
  工具二：精细裁切：把候选时间段的原始帧（最多 60 帧）加字幕交给 VLM，返回可用性评估与内部细分
  工具三：提交 → 交给 Reviewer
  ▼
Reviewer：时长误差 ≤ 1 s、镜头不短于 2 s、不与已用片段重叠、主角出镜比例 ≥ 70%（VLM 看人脸）
  │  不通过：附上问题与建议，退回 Editor 回溯
  ▼
渲染成片（render_video.py）
```

## （3）核心方法

### 抽帧：粗看用低密度采样，按需再取更密的帧

- **低密度采样，2 fps、低分辨率**：镜头描述用的是按 2 fps 采样的低清帧，代码用 240 px，论文写 360p。对 1–3 小时的素材，这是控制成本的第一步。镜头检测不复用这份采样，而是另外打开原视频，按原帧率与 2 fps 之比跳帧读取。
- **镜头检测参数按素材类型区分**：电影用阈值 3.0、最短 3 帧；Vlog 用阈值 1.5、最短 45 帧。最短长度按原视频帧率计（PySceneDetect 的惯例，未逐行核实），30 fps 的视频约为 0.1 s 与 1.5 s。代码与论文都没有说明为什么这样区分；`AdaptiveDetector` 的阈值越低越灵敏，所以 Vlog 这一套是“检测更灵敏、但镜头不能太短”。我们推测：Vlog 的镜头切换常常不如电影剪辑那样画面突变，需要更灵敏才能检测到；同时拉长最短长度，压掉手持晃动造成的碎切。长视频分段并行检测，每段先读一小段“预热”帧，以免在分段边界产生假切点。
- **以物理镜头为描述单位，而不是固定时间窗**：超过 30 s 的长镜头切成子片段，每个子片段配上与它重叠的字幕，一起交给 VLM。这和 Gallery 固定 2 s 窗口的做法相反：镜头边界本身就是天然的剪辑点。
- **精细阶段才回到更密的帧**：精细裁切工具按候选区间取帧，超过 60 帧就等间隔抽稀，并且一定保留最后一帧，让模型知道片段在哪里结束。

### 片段定位：粗筛靠文字结构，精筛靠 VLM 看帧

CutClaw 的检索**完全不用向量**，而是层层收窄范围：

| 层级 | 谁来定位 | 依据 | 输出 |
|---|---|---|---|
| 场景（粗） | Playwriter | 场景的文字摘要（已用人物名替换“一个男人”这类泛称）+ 指令 + 音乐段落描述 | 每个音乐段落分到的场景集合 |
| 镜头（中） | Editor 调用语义邻域检索 | 推荐场景及前后 ±3 个场景里各镜头的“时间段 + 事件摘要 + 情绪” | 候选镜头 |
| 帧级（细） | Editor 调用精细裁切 | 候选区间的原始帧（≤ 60 帧）+ 字幕 | 满足目标时长的 `[入点, 出点]` |
| 校验 | Reviewer | 时长、重叠、主角出镜比例 | 通过，或附带反馈的拒绝 |

几个值得注意的细节：

- **场景聚合用的是加权属性相似度，不是画面向量**：地点类型 30%、时间状态 15%、环境标签集合 35%（标签向量两两比较，取双向最佳匹配的均值）、光线与色调描述的文本向量 20%。
- **桥接镜头前瞻**：插入镜头、反应镜头、特写这类镜头往往打断相似度。遇到它们时，跳过去比较再下一个镜头，避免一个特写就把场景切开。
- **同一个长镜头切出的子片段之间禁止切分场景**，这是硬约束。
- **搜索范围有硬边界**：Editor 只能查看推荐场景前后 ±3 个场景，越界请求直接被工具拒绝，并告诉它可以查哪些。这样既允许“找不到时往邻近找”，又防止模型跑到无关内容上。
- **时长来自音乐**：每条镜头规格的目标时长等于对应节拍区间的长度，同一段落内各镜头时长之和等于段落长度。“剪多长”由音乐决定，而不是由 LLM 拍脑袋。

### 代码与论文的差异

- 论文说 Reviewer 审核美学质量。代码里有美学打分函数（1–5 分，默认门槛 3.0），但在 `core.py`、`Reviewer.py`、`app.py`、`local_run.py` 与渲染脚本中都没找到调用；提交流程实际只检查主角出镜比例和 `review()` 里的规则项，后者的内容匹配检查还写着 `TODO`。
- 论文说 Playwriter 只做场景分配与镜头规划。代码另有一层规则检查：选中的场景必须在 15 个以内，并且要覆盖素材的前、中、后三段。
- 论文的消融实验里，去掉 Reviewer 后 Vlog 的音画同步反而从 87.3 升到 89.4。说明这个审片环节主要在保画面质量和防重复，对节拍对齐略有代价。

### 实验结论的可信度

- 测试集很小：20 个用例。画面质量和指令跟随由 GPT-5.2 打分，音画同步用切点与音乐起始点的偏差（≤ 0.1 s 算对齐）计算。
- 消融结果：去掉音乐结构分析（改为固定长度切分），音画同步从 86.5 降到 77.2；把 Editor 换成随机选片，指令跟随从 70.0 降到 65.6；去掉 Reviewer，画面质量从 77.6 降到 76.0。音乐结构是贡献最大的部分，Reviewer 的贡献最小。
- 论文自述的局限：多阶段流水线处理长素材，推理延迟很高。

## （4）对 A-NAS 的借鉴与创新思考

### 先认清场景差异

| | CutClaw | A-NAS 家庭图库 |
|---|---|---|
| 素材 | 一段 1–3 小时的长素材 | 数百上千段手机短视频（多在 1 分钟以内）加大量照片 |
| 结构 | 镜头 → 场景，都在一条时间线上 | 每段视频本身就是一两个镜头；“场景”更像同一天、同一地点的一次事件 |
| 算力 | 云端 30B 级 VLM 逐镜头描述 | 本地 CPU、离线、空闲时才算；云端模型只用于开发测试 |
| 人物 | 从台词推断角色名 | 已有相册人物库与用户命名（[相册人物](../architecture/photo-people.md)） |
| 音乐 | 必选输入 | 可选：用户可能只要“1 分钟回顾” |

所以不能整套照搬，要拆开借用。

### 可以直接借鉴的

1. **先切镜头，再在镜头里切小段**：先找出视频里画面硬切的位置，把视频分成镜头（工具用 ffmpeg 的 `scdet` 或 PySceneDetect）。每个镜头里再照 [Gallery](https://github.com/google-ai-edge/gallery) 的办法，每 2 秒切一小段，把这 2 秒的几帧画面和声音合成一个向量。搜索找到的是小段，剪的时候可以往前后放宽一点，但不越过镜头边界，免得剪出半截前一个镜头、半截后一个镜头。
2. **每段视频只粗读一遍，大家共用**：这是我们自己的建议，CutClaw 找镜头时是另外读原片的。媒体 Worker 把每段视频低清读一遍（例如每秒 2 帧、短边 360 像素），找镜头、取封面、算向量都用这一份。缺点是每秒 2 帧找到的镜头边界可能差半秒左右：拿来搜索够用，真正剪之前要回原片，把起点和终点对准到具体那一帧。
3. **从大到小一层层找**：先找是哪件事（哪次出游、哪个生日），再找哪几段视频，再找视频里哪个镜头，最后找镜头里哪 2 秒。前面几层用省事的信息筛（拍摄时间、地点、出现的人、整段视频的向量），只有最后一层才精细比对。家里视频一多，必须这样先粗筛再细筛。
4. **每段多长由规则定，不让 AI 猜**：有配乐就跟着节拍切；没配乐就按用户要的总时长和分几段来分。AI 做规划时只说“这一段要几秒、从哪些素材里找、想要什么画面”，具体从第几秒剪到第几秒，交给搜索和规则去定。
5. **能写死的检查就用代码写**：CutClaw 里，时长对不对、镜头够不够长、有没有重复用同一段画面，都是用规则检查的；找素材时不许跑出指定范围，也是查询工具直接拒绝的，都不靠 AI 判断。只有“主角在不在画面里”是让视觉大模型看人脸算的。我们检查剪辑计划也应该用普通代码，能写测试，不合格时能说清楚是哪一条没过。
6. **找不到就有限度地扩大范围**：指定范围里找不到合适素材，就按固定步长往外扩（CutClaw 是前后各扩 3 个场景），超出上限就直接拒绝，不让 AI 漫无边际地到处翻。
7. **别让中间插进来的一个镜头把一件事切成两半**：比如出游视频中间插了一个特写，单看前后像是换了一件事。CutClaw 遇到这种过渡镜头时会跳过它，比较它前后两段像不像，像就仍算同一件事。我们把视频归成事件时也可以这样做。但 CutClaw 是靠视觉大模型给每个镜头标了“这是插入镜头”“这是特写”才认出来的，我们没有这些标注，得换成便宜的判断办法，比如镜头特别短，或者人脸占了画面一大半（近似特写）。

### 需要替换的

- **粗筛的“逐镜头 VLM 描述”换成向量**：给每个镜头跑一次 30B VLM，在 NAS 上不可行。用 EmbeddingGemma 2 的窗口向量做粗筛和中筛；只有进入候选的少量片段，才在需要时交给模型做细判。
- **场景聚合换成事件聚合**：依据拍摄时间间隔、地点、人物重合度，再加上向量相似度，把多段视频和照片聚成“事件”。CutClaw 的加权属性相似度和桥接镜头前瞻都可以照着改写。
- **主角检测接入人物库**：主角出镜比例用相册已有的人脸检测和人物归属直接计算，不用 VLM 逐帧看。
- **美学检查用便宜指标**：模糊度（拉普拉斯方差）、曝光、抖动（帧间光流幅度）、黑场，在解码时顺手算出，作为窗口的质量分。

### 创新点

1. **向量加结构化信号的混合检索**：CutClaw 只有文字，Gallery 只有向量。我们可以结合窗口向量、物体检测、人物、时间与地点元数据，延续相册现有的融合规则思路。
2. **跨资产叙事**：CutClaw 在一条长时间线上剪；我们要在多个事件之间排序（时间顺序、情绪起伏），这是它没有覆盖的问题。
3. **人在回路中的剪辑计划**：CutClaw 是全自动的，我们可以把 Playwriter 的输出作为可编辑的剪辑计划交给用户确认，与 A-NAS“执行计划”的理念一致。
4. **增量与可重建**：家庭图库会持续加入新视频。镜头和窗口索引应该是可重建的派生数据（同照片向量一样记录模型 ID 与参数），CutClaw 是每次从头处理一段素材。

### 待验证

- 在家庭短视频上，场景检测的阈值应该取多少（手机视频多为一镜到底，误切和漏切的代价都要评估）。
- 镜头内窗口向量与整段视频向量在中文查询上的召回差多少，决定是否需要镜头这一层。
- 没有配乐时，“总时长加段落数”的规划能否得到可接受的节奏。
