# 常见后端项目的做法与第八版剪辑的差距

2026-11-16。目的：第八版剪辑要从实验脚本变成能经网页使用的后端服务，先看通行的后端项目怎么组织，再对照第八版，定下一步补什么。参照对象：
- **Immich**：自托管的照片视频服务，同样是上传素材、后台做缩略图、转码和机器学习，和我们最像。来源是它的[架构文档](https://docs.immich.app/developer/architecture)，2026-11-16 读，页面最后更新于 2026-11-11。
- **A-NAS 自己的 Go 服务**：见[架构总览](../architecture/OVERVIEW.md)。
- 业界通行的约定。

## 结论

1. **第八版的分层已经和主流一致。** Immich 的服务端自称“大致按六边形架构”：controller 管 HTTP 接口，service 管业务逻辑，repository 是具体技术的实现。第八版对应的是 `service/`、`domain/` 加 `pipeline.py`、`ports.py` 加 `adapters/`，不用再改结构。
2. **差的是“服务化”的那几块：**
   - 持久的任务队列；
   - 数据库；
   - 接口契约；
   - 登录；
   - 断点续传；
   - 日志和健康检查。

   这些都有成熟的库和协议，按项目规矩不手写。
3. **建议的下一步是任务层。** 网页“开始剪辑”只建一个任务，后台 Worker 一次跑一个，网页查进度、取成片。用 SQLite 记任务，不额外引入 Redis。

## 通行做法

| 方面 | 通行做法 | Immich | A-NAS（Go 产品服务） |
|---|---|---|---|
| 分层 | 接口层 → 业务层 → 数据访问或适配层，业务层不依赖框架（六边形、整洁架构） | controllers → services → repositories；DTO 是接口的输入输出类型 | `internal/<领域>` 不依赖 HTTP，`internal/<领域>api` 管接口（#192） |
| 接口契约 | OpenAPI 描述接口，客户端代码从契约生成 | DTO 生成 OpenAPI，网页、手机、命令行三端都自动生成客户端 | `api/openapi.yaml`，Web 类型与响应校验从契约生成（#220） |
| 耗时的活 | 请求只建任务，由后台 Worker 从持久队列里取；任务能重试、能看进度；一个任务完成后触发下一个 | 后台任务用 Redis + BullMQ 排队；缩略图做完自动触发智能搜索和人脸识别 | systemd 按需启动的 AI Worker（ADR 0016） |
| 机器学习 | 单独的进程或容器，经 HTTP 调用；模型大、占内存，和接口服务分开 | Python + FastAPI 的独立容器，ONNX 模型，下载后缓存；用线程池跑模型，不阻塞异步事件循环 | AI Worker 无网络、只读描述符 |
| 数据 | 关系数据库存状态，结构变更用迁移脚本，文件放磁盘或对象存储 | Postgres；配置也存库里；有迁移文档 | SQLite（`internal/sqlitedb`） |
| 上传 | 大文件分片、能续传（tus，或对象存储的分片上传） | 文档未写 | tus（`/api/v1/uploads`，ADR 0019） |
| 配置 | 启动时从环境或配置文件读一次并校验，不同环境只换配置（十二要素应用） | 文档未写 | 启动时解析并校验，没有默认值的必须给（不变量 19） |
| 登录 | 会话或令牌，接口按身份授权 | 文档未写 | 会话 Cookie + CSRF，按路由的姿态统一检查 |
| 可观测 | 结构化日志、健康检查接口、指标 | 文档未写 | 系统日志接口、白名单 journal 查询 |
| 部署 | 容器或系统服务，一个进程一个职责 | 4 个 Docker 容器：server、machine-learning、postgres、redis | systemd 单元，按身份分进程 |

Immich 文档里有一处前后不一：容器清单只列了 `immich-server`，示意图却还有专门处理队列任务的 `immich-microservices`。所以它现在是否把接口和后台任务分进两个进程，以这页为准说不清。

## 第八版对照

| 方面 | 第八版现在 | 差距 | 建议 |
|---|---|---|---|
| 分层 | `domain/` 纯规则，`ports.py` 加 `adapters/`，`pipeline.py` 编排，`service/` 入口 | 无 | 保持；Ruff TID251 继续守住领域层 |
| 耗时的活 | 命令行一次跑完；网页的“开始剪辑”还是示例 | 没有任务队列，没有进度，网页触发不了剪辑 | 任务层：SQLite 记任务（状态、当前步骤、进度、出错原因），一个 Worker 线程或进程按顺序执行；编排层已有的“结果存在就复用”让中断的任务能接着跑 |
| 数据 | 卡片、规划是整份 JSON，读出、改完、整份写回 | 两个任务同时写会互相覆盖；查询要整份读 | 任务状态先放 SQLite；卡片等结果文件暂时不动，以后再迁 |
| 接口契约 | 手写的路由，没有契约 | 网页靠约定调用 | 写进 OpenAPI。放进 A-NAS 时用 `api/` 的契约和生成的类型；Starlette 本身不生成 OpenAPI，若单独成服务可换 FastAPI |
| 上传 | 整个文件一次 PUT，断了重传 | 大文件不能续传 | 换成 tus：浏览器用 tus-js-client，服务端用现成实现。放进 A-NAS 时直接用它已有的 tus 上传 |
| 登录 | 没有，只开在本机 | 不能开放到局域网 | 放进 A-NAS 时做成可移除模块（ADR 0037），登录和会话交给 A-NAS；单独部署时至少加一个访问口令 |
| 机器学习 | 视觉模型是独立的 llama-server，经 HTTP 调用 | 与通行做法一致 | 保持；板子上换 RKLLM 服务只换地址 |
| 配置 | TOML 配置 + 环境变量覆盖，启动时读 | 没校验缺项 | 启动时校验，缺项直接报错 |
| 可观测 | 打印到标准输出 | 没有健康检查，没有结构化日志 | 加 `/healthz`，日志用标准库 logging 输出 JSON 行 |
| 部署 | 手动起 Python | 没有服务单元 | 板子上写 systemd 单元，与 A-NAS 的部署方式一致 |

## 为什么不照搬 Immich 的 Redis + 队列库

Immich 同时有很多种后台任务，又要支撑多个用户，所以值得用 Redis 加 BullMQ。我们的剪辑一台机器一次只能跑一个任务（描述和渲染吃满 CPU 或 NPU），任务量很小。用 SQLite 一张任务表、一个 Worker 就够了，板子上也少起一个服务。

将来任务种类变多、需要多台机器分摊时，再换成现成的任务队列库。Python 生态里常见的有 Celery、RQ、Dramatiq；要选哪一个，到时候再比较，不在这次定。
