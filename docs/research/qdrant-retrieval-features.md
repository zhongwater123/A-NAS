# Qdrant 检索特性试验（1.20.0）

> 状态：完成（开发机试验，2026-10-26）；结论供 ADR 0028、视频片段与文件块索引的设计取用  
> 更新日期：2026-10-26  
> 适用范围：Qdrant 1.20.0 官方 musl 二进制（`qdrant-x86_64-unknown-linux-musl.tar.gz`，sha256 `b03a64616a1f41ddab78b480a318466541765f19835318113b1821cbea8df52c`），qdrant-client 1.20.0（gRPC）；照片与文本向量为 `embeddinggemma-2-740m@e7a8a2204b91+mediapipe-1.1.0+tok70+l2`（768 维，L2 归一化，Dot 距离）  
> 关联：[issue #66](https://github.com/zhongwater123/A-NAS/issues/66)、[相册物体检测与混合检索可行性](photo-ai-object-detection.md)、[M2 实施方案](../architecture/photo-ai.md)

A-NAS 把 Qdrant 作为可重建的派生向量索引：SQLite 仍是事实源，每个拥有向量的服务（先是相册，之后是文件索引）各自按需启动一个 Qdrant 实例，经 Unix 套接字代理访问，数据放在系统 NVMe 上。这一步相册只把向量镜像进 Qdrant 并做影子比对；推翻 #66 "不引入独立向量数据库"的决定由 ADR 0028 记录。本文用开发机上的真实向量逐项试用 Qdrant 1.20.0 的检索特性，回答三件事：视频片段与文件块索引该用哪些特性；照片搜索什么时候可以切到 Qdrant；人脸聚类要的"阈值以上的全部邻居"能否交给 Qdrant。

## 结论

1. **照片**：10 万张以内，Qdrant 的精确检索与相册现行的进程内精确扫描同一量级（10 万张取前 500：Qdrant 16–20 ms，numpy 单线程 10–18 ms），没有速度收益。默认配置在 2 万张时就会建 HNSW（4 个段各约 15 MB，超过 10 MB 的建图阈值），按图库过滤取前 500 的召回均值 0.96–0.99，个别查询低到 0.6。影子比对必须用 `exact: true`，否则比出的差异主要是 HNSW 的近似误差。切换条件见“照片搜索的切换条件”。
2. **视频片段**：一个视频一个点、片段作 `max_sim` 多向量且不建图（`m: 0`），分数与“视频分 = 最佳片段的点积”逐位一致（差 ≤ 6×10⁻⁷），3 万个片段上 p50 约 6 ms，与 numpy 单线程相当。一片段一点加 `query/groups` 在 `exact: true` 时同样精确，但走 HNSW 时前 100 个视频只找回约 90%，且不能翻页；均值向量预取再 MaxSim 重排在预取 200 个时前 10 召回仍只有 0.98。
3. **文件块**：在仓库中文文档的 42 条问题上，稠密向量 Hit@1/5/10 为 0.52/0.81/0.93，`multilingual` 分词的 BM25 为 0.41/0.76/0.83，两者用 DBSF 融合为 0.52/0.88/0.93、MRR 0.685，是几种排序里最好的；RRF 的默认 k = 2 比 k = 60 略好。样本小，一条问题相当于 2.4 个百分点，融合相对稠密在前 5 上净多答对 3 条。中文分词是词级的，可用。另外两点要进设计：MediaPipe 的文本编码器最多 1,024 个 token，超长输入直接报错，切块要按 token 而不是 1,800 个字符；带全文索引的集合冷启动后第一次查询要 0.4–0.9 s。
4. **检测融合**：`formula` 能逐位复现相册的检测融合规则（差 ≤ 6×10⁻⁷），前提是给公式用到的每个变量写默认值 0；候选只取向量前 500 时前 10 有 2/630 条查询变化，再加一路“检测到”分段的预取即全部一致，p50 约 9 ms。
5. **人脸**：确认 #66。3 万张合成人脸取“阈值以上的全部邻居”，numpy 单线程 12.7 s，Qdrant 分页阈值查询 151–257 s，`search_matrix` 只找回 17% 的邻居对；LFW 真实向量上 numpy 4.6 s，Qdrant 16–41 s。新脸增量 numpy 1.8–2.8 ms，Qdrant p50 6–14 ms、p95 最高约 150 ms，HNSW 下还会漏邻居。
6. **运维**：冷启动（页缓存已逐出）到首个查询完成 0.2–1.0 s，适合按需启动。批量写入时磁盘和文件映射 RSS 会冲高：10 万张默认配置建完时磁盘 2.0 GB、RSS 峰值 2.9 GB，重启后分别回到 0.35 GB 和 0.46 GB。`wal_capacity_mb: 1` 让稳定后的 WAL 从 37–45 MB 降到 2–3 MB（默认配置刚建完时 WAL 达 73–372 MB），未见代价。

### 照片搜索的切换条件

现行实现每次搜索在进程内对调用方可见的图库做精确扫描（[`internal/photos/search.go`](../../internal/photos/search.go)，取前 `maxSemanticResults = 500`）。试验没有发现 Qdrant 在 10 万张以内带来延迟收益，切换的理由只能是内存与重建边界（向量离开相册进程，由 mmap 按需载入），而不是速度。建议：

1. 影子比对阶段：Qdrant 查询一律 `exact: true`，按图库 `match any` 过滤，取前 500；以本文的并列口径（分数在第 k 名的 10⁻⁵ 以内算命中）比较，预期召回为 1。任何低于 1 的差异都应当是镜像不同步，而不是近似误差。
2. 读路径切到 Qdrant 的条件：影子比对在真实图库上连续一段时间召回为 1；同一批查询的 p95 延迟不高于现行扫描加上 Unix 套接字代理的往返开销。
3. 改用 HNSW 的条件：单个成员可见的照片超过约 10 万张，且精确检索 p95 超出搜索延迟预算。那时取前 500 要设 `hnsw_ef` ≥ 2000，否则个别查询的召回会低到 0.6。

## 环境与方法

### 运行方式

- **二进制**：GitHub v1.20.0 发布的 `qdrant-x86_64-unknown-linux-musl.tar.gz`（33,773,335 字节），sha256 与发布页一致（见文首）；解包得到静态链接的 `qdrant`，`qdrant --version` 为 `qdrant 1.20.0`。不用 Docker 镜像（开发机也连不上 Docker Hub）。
- **遥测**：默认配置 `telemetry_disabled: false`；试验同时用 `--disable-telemetry` 和 `QDRANT__TELEMETRY_DISABLED=true` 关掉。服务只监听 127.0.0.1，端口 16333/16334，避开本机产品栈可能占用的 6333/6334。
- **进程**：评估脚本在 `anas-ai-dev:trixie` 容器里把官方二进制作为子进程启动，以便测冷启动时停掉、逐出页缓存、再启动。存储放在 WSL 自己的 ext4 上，不放 `/mnt/d`。容器用 `--cpuset-cpus 0-7` 限 8 个逻辑 CPU，与实验 NAS 的 i3-12100（4 核 8 线程）一致，Qdrant 按 CPU 数推出的默认值（段数 4、建图线程）与设备上相同；单线程性能不同，绝对延迟只看量级。
- **客户端**：qdrant-client 1.20.0 走 gRPC，装在评估专用的 venv 里，依赖按哈希锁定在 [`ai/eval/qdrant-requirements.lock`](../../ai/eval/qdrant-requirements.lock)，numpy、scikit-learn、MediaPipe 来自开发镜像。
- **默认值**：1.20.0 默认关闭严格模式与节点配额，试验的大 `limit`、无索引过滤都能执行；产品若开启严格模式，要按这里用到的上限设置 `max_query_limit` 等。

### 度量口径

- **正确性**：照片、视频、人脸以 numpy 精确计算为参照；检测融合以 [`eval/hybrid_search.py`](../../ai/eval/hybrid_search.py) 的 `product()`（与 Go 实现一致）为参照。召回按并列计：结果中精确分数不低于第 k 名分数减 10⁻⁵ 的点都算命中，因为 Qdrant 的 SIMD 与 numpy 的 BLAS 求和顺序不同。完全相同的向量（COCO-CN 与 COCO 2017 重复的照片）只留一份；以图搜图的查询照片本身从结果和参照里都去掉。
- **延迟**：客户端计时，含 Python gRPC 的往返；同一集合上“不打分的查询”（按不存在的 id 过滤）作底，多为 1–3 ms。numpy 参照限单线程，对应相册在一次搜索内逐张循环的扫描（`search.go` 的 `dot`）；Go 的标量循环比 BLAS 慢，现行实现的实测耗时未测。
- **冷启动**：停进程后对存储目录每个文件 `fsync` 并 `posix_fadvise(DONTNEED)`，再启动，记录 gRPC 端口可连、`/readyz` 返回 200、首个查询完成三个时刻，取 3 次中位数。开发机没有 root，不能清整个页缓存；WSL 的虚拟盘还有 Windows 一层缓存，结果偏乐观。
- **内存与磁盘**：RSS 读 `/proc/<pid>/status` 的 VmRSS、VmHWM 及匿名、文件两部分；文件部分是 mmap 的向量与图，可被回收，但在 cgroup v2 里计入服务的内存。磁盘按实际分配的块计；Qdrant 预分配稀疏文件，表观大小是它的 3 倍以上，小集合可达 30 倍。

## 固定行为（1.20.0）

下列行为读自 v1.20.0 的源码，并由 `qdrant_facts.py` 在小集合上实测确认（报告 `facts-20261026-101825.json`，全部通过）。

| 行为 | 源码位置 | 实测 |
|---|---|---|
| RRF 不带参数时 k = 2，名次从 0 计，单路贡献 1/(名次 + k) | `lib/segment/src/common/reciprocal_rank_fusion.rs`（`DEFAULT_RRF_K = 2`） | 两路第一名合计 0.5；与 `{"rrf": {"k": 2}}` 结果相同；显式 `k: 60` 时单路第一名贡献 1/60，不是文献写法的 1/61。[`hybrid_search.py`](../../ai/eval/hybrid_search.py) 的 `rrf_rank` 用 1/(60 + 1 + 名次)，即文献写法 |
| DBSF 每路按均值 ± 3 个样本标准差缩放后相加，不截断 | `lib/segment/src/common/score_fusion.rs` | 与按此公式重算的差 2×10⁻⁷ |
| `multilingual` 分词器含 charabia 的中文分词（构建开启 `chinese-segmentation`、`chinese-normalization`） | `lib/segment/Cargo.toml` | 文本“相册里的照片按时间排列”：查“照片”“相册”命中，查单字“片”不命中；“南京市长江大桥”可用“长江大桥”“长江”命中，“江大”不命中；繁体“相冊”不会归一成简体“相册”。`word` 分词器把整段汉字当一个词，以上查询全部不命中 |
| `query/groups` 没有 offset | OpenAPI `QueryGroupsRequest` 没有该字段，REST 结构体也不拒绝未知字段 | 带 `offset: 3` 的请求返回 200，结果与不带相同，即静默忽略；只能加大 `limit` 重取 |
| `query/groups` 分轮执行：每轮取 组数 × 每组条数 个候选，并用过滤条件排除已找到的组，最多 5 轮收集、5 轮补齐 | `lib/shard/src/grouping/driver.rs`（`MAX_GET_GROUPS_REQUESTS = 5`） | 实验 2：`exact: true` 时 100 个组全部正确；走 HNSW 时每轮都是带排除条件的过滤检索，前 100 召回约 0.90 |
| MaxSim 对每个查询行取文档各行的最大相似度再求和；一行查询即最佳片段的点积 | `lib/segment/src/vector_storage/query_scorer/mod.rs` | 一行查询与 numpy 差 6×10⁻⁸，两行查询差 2.4×10⁻⁷ |
| `formula` 引用的 payload 变量缺失且没有默认值时报错 | `lib/segment/src/index/query_optimization/rescore_formula/formula_scorer.rs` | 报错为 `Expected number value for x in the payload and/or in the formula defaults. Error: No value found in a payload nor defaults`；给 `defaults` 后按默认值计算。嵌套路径 `obj.c7` 可用；数组字段 `arr` 整体报 `Value is not a number`，`arr[1]` 可用；`$score` 缺失时按 0 |
| MMR 的 λ = 1 − diversity，先取最相关的一条，再逐条取 λ × 相关度 − (1 − λ) × 与已选的最大相似度 | `lib/shard/src/query/mmr/mod.rs` | 实验 5：Qdrant 的顺序与按此实现的 numpy 完全一致 |
| `search_matrix` 先随机抽 `sample` 个点，再对每点在样本内做 `limit + 1` 的近邻查询，不支持阈值和搜索参数 | `lib/collection/src/collection/distance_matrix.rs` | 实验 6 |

## 实验 1：按图库过滤的照片检索

## 实验 3：文件块

语料是仓库 `docs/`（提交 `6f25568`，不含本文）：127 个文件按标题切成 1,484 块（#152 文本研究的切法：`#` 到 `####` 分段，不足 80 字并入前一块，超过 1,800 字按空行再切）。42 条中文问题各标明答案所在的章节，命中该章节的任一块即算答对。稠密向量用产品的 `.litertlm` 经 MediaPipe 计算，中位 0.5 s 一块。

- **文本窗口**：MediaPipe 的文本编码器最多 1,024 个 token，超长时直接报错（`Input sequence length (1099) exceeds maximum supported signature length (1024)`），不会自动截断。1,484 块中有 13 块超长，评估时取能编码的最长前缀（至少保留了 78% 的字符）。产品切块要按 token 数（含前缀）控制在 1,024 以内，不能按 1,800 个字符。
- **BM25**：`text` 字段建全文索引，`tokenizer: multilingual`、`lowercase: true`、`scoring: true`（BM25 默认 k1 = 1.2、b = 0.75），用 `{"text": "<问题>"}` 查询，含任一个词的块就有分。
- **融合**：两路各预取 50 块，分别用 RRF（默认 k）、RRF（k = 60）、DBSF 融合；文件级结果另用 `query/groups` 按 `path` 分组（每组 1 块，取 5 组）。

## 实验 4：用 formula 复现检测融合

相册的规则（[`internal/photos/search.go`](../../internal/photos/search.go)、`hybrid_search.product`）：排序分 = 向量分 + 权重 0.2 × 物体词占比 × 各启用词“其类别中最高检测分”的最小值；查询以可靠物体词为主时，每个词都达到各自分数线的照片作为“检测到”分段排在最前。写成公式：每张照片的 payload 存各类别的最高检测分 `det.c<类别>`（没检测到就不存），

`Sum($score, Mult(0.2 × 占比, Min(Max(det.c…), …)), Mult(10, Min(每个词一个条件：任一类别 ≥ 该词分数线)))`

占比与词到类别的映射在查询时由相册算好，公式里每个变量都给默认值 0（与 Go 对“没检测到”的处理相同）。数据为 16,126 张有检测结果的照片，查询为 330 个词表标签名加 300 条 COCO-CN 描述，其中 351 条含启用的物体词，66 条进入“检测到”分段。

| 候选 | 分数最大差 | 前 10 召回 均值/最差 | 前 50 召回 均值/最差 | 前 10 有变化的查询 | p50 / p95 ms |
|---|---|---|---|---|---|
| 全部照片（精确预取 16,126） | 6×10⁻⁷ | 1/1 | 1/1 | 0 | 103 / 367 |
| 向量前 500 | 6×10⁻⁷ | 0.9994/0.7 | 0.9977/0.28 | 2 | 9.0 / 18.5 |
| 向量前 500 + “检测到”分段的预取 | 6×10⁻⁷ | 1/1 | 0.9991/0.72 | 0 | 9.1 / 55.0 |

同一批查询：不带公式的精确检索 p50 10.4 ms；numpy 计算 `product()` p50 0.4 ms。

- 公式在全部候选上与 Go 等价，但每个候选都要读 payload，1.6 万张 p50 103 ms，不能这样用。
- 候选只取向量前 500 时，加分（最多 0.2）可能把第 500 名之外的照片抬进前列：按“向量分 ≥ 第 50 名融合分 − 0.2 × 占比”估算，保证前 50 不变需要的预取中位 52 张、p95 553 张，最坏是整个图库。“检测到”分段的照片向量分可能很低，必须单独预取：第二路预取用分段条件作过滤、同样按向量打分，公式里取 `Max($score[0], $score[1])`（两者缺失时默认 −1），前 10 即全部一致。
- 缺默认值时报错（见固定行为），所以公式引用的每个 `det.c<类别>` 都要写进 `defaults`。检测分按类别存成对象字段（本实验的做法）或数组都可以，数组要用下标路径（`arr[1]`）取，整个数组不能当数字用。

## 实验 6：人脸“阈值以上的全部邻居”

阈值为产品 AuraFace 的 0.48（[`internal/photos/people.go`](../../internal/photos/people.go)）。合成集按 LFW 的 AuraFace 统计生成：人与人之间、同一人内部的主成分（各 64 个）加各向同性残差，同一人内部的离散度缩放到让同人余弦中位与 LFW 一致。每人的脸数服从指数 0.8 的 Zipf 分布，与 #66 的规模相当。

| 集合 | 脸 | 同人余弦 中位 / 10% | 异人余弦 中位 / 99.9% | 每张脸的邻居 均值 / 最多 |
|---|---|---|---|---|
| LFW（AuraFace） | 16,944（另 200 张作新脸） | 0.606 / 0.443 | 0.059 / 0.294 | 25.5 / 530 |
| 合成（600 人，最多 2,212 张，中位 23 张） | 29,800（另 200 张作新脸） | 0.601 / 0.530 | 0.106 / 0.360 | 362.9 / 2,198 |

Qdrant 的取法：对每个点按 id 查询，`score_threshold` 0.48，每页 256 条，满页就用 offset 翻下一页，64 个查询一批；另用 `search_matrix_pairs` 对全部点、每点 64 条。

| 集合 | 方法 | 用时 s | 邻居对召回 | 邻居全部找到的脸 | 新脸 p50 / p95 ms（找全的比例） |
|---|---|---|---|---|---|
| 合成 | numpy 分块矩阵乘，单线程 / 8 线程 | 12.7 / 8.3 | 1 | 1 | 2.8 / 3.6（1） |
| 合成 | Qdrant 默认配置（已建图）阈值查询 | 151 | 1.0 | 0.9992 | 7.5 / 135（0.875） |
| 合成 | Qdrant `exact` 阈值查询 | 257 | 1 | 1 | 14.0 / 152（1） |
| 合成 | Qdrant 强制建图，`hnsw_ef` 128 | 159 | 1.0 | 0.9988 | 7.8 / 124（0.83） |
| 合成 | Qdrant 强制建图，`hnsw_ef` 512 | 198 | 1.0 | 0.9994 | 13.1 / 141（0.84） |
| 合成 | `search_matrix_pairs`，每点 64 条 | 113–115 | 0.173 | 0.458 | — |
| LFW | numpy 分块矩阵乘，单线程 / 8 线程 | 4.6 / 2.3 | 1 | 1 | 1.8 / 2.9（1） |
| LFW | Qdrant 默认配置（未建图）阈值查询 / `exact` | 28.2 / 26.8 | 1 | 1 | 7.4 / 12.4（1）；6.4 / 13.8（1） |
| LFW | Qdrant 强制建图，`hnsw_ef` 128 / 512 | 16.2 / 40.7 | 1 | 1 | 6.1 / 14.5（1）；10.3 / 24.8（1） |
| LFW | `search_matrix_pairs`，每点 64 条（未建图 / 建图） | 17.7 / 54.4 | 0.447 | 0.877 | — |

合成集每张脸平均 363 个邻居、8,893 张脸超过一页（256 条），按页翻完共 61,553 次查询；LFW 平均 25.5 个，512 张超过一页。

- 结论与 #66 相同：这一步是“每张脸返回几百上千条”，不是近邻查询。Qdrant 按点逐个查询再翻页，比一次矩阵乘慢一个数量级；新脸也慢，大人物要翻好几页，p95 到 120–150 ms；合成集在 HNSW 下有 13%–17% 的新脸找不全。全量时一对邻居只要从任一方向查到就算找到，两次机会掩盖了 HNSW 的漏检；新脸只有一次。LFW 的人小、邻居少，差距缩到 3–9 倍，方向不变。
- `search_matrix` 没有阈值、每点条数固定，又不接受搜索参数，不适合这一步。人脸聚类继续用进程内矩阵乘（[`ai/eval/people.py`](../../ai/eval/people.py) 的做法），人脸向量不进 Qdrant 也不影响聚类。

## 限制

- 没有在实验 NAS 上运行。开发机的单线程性能、内存带宽和磁盘与 i3-12100 + NVMe 不同；冷启动没有清 Windows 一侧的缓存，偏乐观。
- 延迟包含 Python gRPC 客户端的开销（多为 1–3 ms），产品经 Unix 套接字代理和 Go gRPC 客户端，开销不同。
- 开发机的速度在一天内变化很大：同一个 numpy 计算在视频实验的两次运行中分别是 5.1 ms 和 17.3 ms。各表的延迟只与同一次运行里的 numpy 参照比较，跨表不比绝对值。
- HNSW 的召回在不同构建之间有波动：10 万张时六种变体都用默认搜索参数，成员 a 前 50 的最差单条从 0.24 到 0.74，表中每格只有一次构建；结论只依赖精确检索和量级。
- 10 万张中 6.3 万张是合成的近邻混合；视频是照片拼的伪视频，片段间的相似度结构与真实视频不同；人脸合成集只匹配了 LFW 的同人余弦中位。
- 文件块的 42 条问题来自仓库文档，答案只标一个章节，一条问题相当于 2.4 个百分点。
