# 相册物体检测与混合检索（切片 18）实施方案

状态：accepted（2026-10-13 用户确认）；全部 10 步已实现（[#83](https://github.com/zhongwater123/A-NAS/pull/83)）。阈值文件按官方导出的模型生成，结果见[研究](../research/photo-ai-object-detection.md#官方导出与产品规则2026-10-13)
更新时间：2026-10-23

本文把[相册技术设计](photo-library.md)的切片 18 细化为可实现的方案：后台为每张照片检测物体，文搜图把检测结果与照片向量融合，以物体词为主的查询如实说出“检测到”或“没有检测到”，并新增以图搜图。依据见[物体检测与混合检索研究](../research/photo-ai-object-detection.md)；方案复用 M2 的 Worker、持久任务、空闲门控与内置交付（[相册本地 AI](photo-ai.md)、[ADR 0016](../adr/0016-ship-photo-ai-as-a-built-in-offline-capability.md)）。

## 目标与范围

完成后，成员可以：

- 搜“手机”“杯子”这类物体时找回不到画面 1% 的小物体（COCO 上召回从 36% 升到 72%），并看到“检测到手机的照片 N 张”；图库里没有时看到“没有检测到手机”，整理尚未完成时同时看到还有多少张没识别完；
- 用一句话描述照片时得到与现在相同质量的排序（COCO-CN 上 R@1 71.5% 对 71.3%）；
- 在查看器里点“找相似”，看到与这张照片内容相近的其他照片。

已定的决定（2026-10-10 至 2026-10-13）：

- 检测器为 D-FINE Objects365 M（365 类），由 ONNX Runtime 在 CPU 上运行；发行用的 ONNX 由我们以官方权重和官方导出脚本自行导出。作者对 Objects365 权重的商用声明不影响内部测试，对外发行前单独确认。
- 界面对以物体词为主、且该类已评估启用的查询可以说“检测到 / 没有检测到”；句子类查询仍只说“最接近”。
- 红线不变：由向量模型产生的标签不参与搜索。检测器的类别不由向量模型产生，可以参与搜索。
- 资源：闲时有多少资源就用多少，但始终留出余量应对用户的突发请求；用户有突发请求时 AI 要正确释放资源。

不在范围内：查看器显示物体框、由检测结果组成的 AI 聚合、切片推理（等真实的 1200 万像素照片评估后再定）。

## 整体结构

```text
anas-photos ──UDS + 只读 fd──► anas-ai（一个进程）
  │  任务：thumbnail/v1 → embedding/v1、objects/v1           ├ MediaPipe：EmbeddingGemma（向量，搜索也要用）
  │  Catalog：embeddings、detections                           └ ONNX Runtime：D-FINE（检测，只在后台任务时加载）
  │  内存索引：照片向量、每张照片每类的最高检测分
  └  搜索：名称/用户标签 → “检测到”分段 → 融合排序；以图搜图
```

一个 Worker 进程装两个 Provider：两个进程要重复加载 Python 与 numpy，单元、套接字、沙箱、安装器与系统测试也都要各做一份；一个进程由相册服务统一调度，资源用量只有一处可控。人脸方案（[#64](https://github.com/zhongwater123/A-NAS/pull/64)）也放在同一个 Worker。

## Worker

- **检测 Provider**：启动时按清单核对 ONNX 文件的大小与 SHA-256；第一次检测时才创建 ONNX Runtime 会话。模型 ID 为 `<名称>@<SHA-256 前 12 位>+ort-<版本>+640+s0.05k100`，即 640 输入、保留分数不低于 0.05 的前 100 个框；预处理与评估一致，缩放到 640×640、不保持长宽比。改成切片推理只改 Worker 与模型 ID，旧结果随模型变化自动重排。
- **协议**：新操作 `detect_objects` 接收一个只读 fd，返回模型 ID 与若干 `(class, score, x0, y0, x1, y1)`，坐标为 0–1 的比例；`release` 卸载检测会话（可选地连同向量模型）。`info` 只在检测器可用时多报一个 `detector` 字段。官方导出的图已包含后处理，输入为 `images` 与 `orig_target_sizes`，输出 `labels`、`boxes`、`scores`，Worker 的后处理据此编写。
- **可用性按能力区分**：向量模型不可用时整个 Worker 不可用（与现在相同）；检测器不可用只影响 `detect_objects`。
- **取消**：推理在单独的线程中执行，主线程同时监视连接；相册服务关闭连接（取消任务的 context）时设置 ONNX Runtime 的 `RunOptions.terminate`，几毫秒内中止，Worker 不回应。MediaPipe 的向量推理无法中途取消。
- **测试替身**：Fake 检测器只用标准库，按输入的哈希给出确定的框。

## 检测输入

相册服务为每个检测任务解码原图、按 EXIF 方向转正、透明处合成白底、缩放到长边 1600 px、编码为 JPEG（质量 92），写入密封的 `memfd` 后以只读描述符传给 Worker，不落盘；非 Linux 平台退回到已删除路径的临时文件。512 px 的缩略图小于评估所用的输入，640 px 长边又会让短边在缩放到 640×640 时被拉伸，所以采用与人脸方案相同的 1600 px，以后两者共用。解码、转正与合成白底从缩略图的渲染中抽出共用，解码器 panic 与缩略图一样记为无法解码。

渲染在一个核上进行。为了不让 Worker 的线程等它，Worker 检测当前一张时，相册服务已经领取下一个检测任务并渲染它的输入（2026-10-13 实机首次运行后加入）。如果接下来先做向量、门控关闭或服务停止，这个任务回到队列原位，不计尝试次数。

## 任务与存储（Catalog migration 7）

- `detections(object_id, derivation, model, boxes, created_at)`，主键 `(object_id, derivation)`，随对象级联删除。`boxes` 为 1 字节版本号加每框 14 字节（类别 2 字节、分数 float32、四个角各 2 字节）；空列表表示处理过、什么也没检测到。与评估一致，保存分数不低于 0.05 的前 100 个框，每张约 1.4 KB。检测结果以内容对象为键，副本与重复照片共用。
- 同一个 migration 为已有缩略图补排 `objects/v1` 任务（做法同 migration 4）；之后缩略图完成时在同一事务中同时排入 `embedding/v1` 与 `objects/v1`。
- 后台先做向量任务、再做检测任务；只在最近一次 `info` 报告了检测器时才领取检测任务，否则坏掉的检测器会不断唤醒 Worker、使它无法空闲退出。检测响应的模型与 `info` 不一致时退回任务。已知模型与换模型时的重排按任务类型分别记录。
- 内存中按对象保存每个类别的最高分，只载入阈值所校准的模型的结果；模型不符时不融合、不分段，避免说错。新结果写入时更新，清除照片时与向量索引一起删除。
- AI 状态：“已整理”指向量与检测结果都有；“失败”指未整理且缩略图、向量或检测任务之一已彻底失败；新增 `objectModel`。升级到本版本后进度会从“已整理全部”回到“0 / N”，这是如实的。

## 类别与启用名单

- 中文类名、同义词、覆盖多个类别的词（鞋子、鸟、水果、宠物等）与整体跳过的词（马路、上面等）只有一份：[`internal/photos/objects/v1.json`](../../internal/photos/objects/v1.json)，随程序发布，评估脚本读同一个文件。
- 匹配为最长匹配（“热狗”不算“狗”），物体词占比按字计算，标点集合与评估相同；以 Python 匹配器生成的约 150 条查询的标准答案文件做 Go 的回归测试。未启用的词照样被匹配“吃掉”，只是不加分。
- 阈值文件 `v1.calibration.json` 由评估生成、不手改：`model`、`weight`（0.2）、`tierCoverage`（0.6）、类别级的融合名单 `fusion`，以及按词记下的测量结论 `words`。
  - 一切只在校准半（COCO 与 Open Images 各一半）上选出，测试半只用来报告结果，不参与选择。
  - **按词的结论**（2026-10-13 起）：单独测过的词按它所指的类别集合记一条，例如“汽车”是 `6,35,50,88,127,309`，同义词指同样的类别，共用这一条。
    - `fusion`：在校准半上融合后的平均精度平均不低于纯向量减 0.02。组合词凭它自己的测量启用，不再因为其中有没单独测过的类别（SUV、皮卡等）而整体关闭。
    - `tierScore`：这个词自己的“检测到”分数线。要求在测到它的每个数据集上，至少 85% 正确并收入至少一半真实照片；研究用的 0.6 合格就用 0.6，不合格时取离 0.6 最近的合格分数，在 0.25–0.90 之间按 0.05 取值，只动到刚好合格为止；都不合格则不分段。
    - 取最低合格分数会让本来在 0.6 就合格的词降到 0.25–0.4，误报明显变多（见[研究](../research/photo-ai-object-detection.md#官方导出与产品规则2026-10-13)）。
  - **没单独测过的词**：它所指的类别都在融合名单上才启用；没有分数线，不分段。融合名单是被至多覆盖三类的已测词提到、且这些词都没变差的类别。
  - 2026-10-13 起 Open Images 的人工核验标注按正确的方式读：`1.0` 也是“有”，之前被当成“没有”（[调查](../investigations/2026-10-13-open-images-positives-read-as-absent.md)）。
  - 约 240 个没有真值的类别与含义待核实的条目只存储、不启用。

## 搜索

- **融合分** = 余弦相似度 + 0.2 × 物体词占比 × 检测分；检测分取查询中各个词的最低分，每个词取它对应类别里最高的框分。
- **分档**：名称或用户标签匹配为 6 + 融合分，“检测到”分段为 3 + 融合分，其余为融合分；每档跨度至多约 [−1, 1.2]，互不重叠，现有的分数游标与翻页不变。
- **以物体词为主的查询**：物体词占比 ≥ 0.6，且提到的每个词都启用、都有自己的分数线。每个词的最高类别分都达到该词分数线的照片组成“检测到”分段，不设上限；其余照片最多 500 张。`closest` 为名称匹配数加分段张数；分段为空时退回“与最佳结果相差 0.04 以内”，在融合分上计算（第 2 步按产品规则重跑后沿用）。
- **响应**新增可选的 `objects: {words, detected, undetected}`：`undetected` 是范围内还没有检测结果的照片数，界面据此说明“还有 N 张尚未识别完”，否则“没有检测到”在整理期间是假话。分段只用已存储的结果，Worker 不可用时（`semantic: false`）照样有效。
- 向量产生的 AI 聚合仍不参与搜索（`TestSearchNeverUsesClusters` 保留）。

## 以图搜图

- `GET /api/v1/photos/assets/{assetId}/similar?viewing=&cursor=&limit=`：范围与搜索相同；源照片须可见、不在回收站、在范围内，否则与不存在一样返回 404。按已存储的照片向量的余弦相似度排序，不需要 Worker；排除同一内容对象的照片，最多 500 张。返回 `{items, next, ready}`，源照片还没有向量时 `ready` 为 false。
- 共有物体的加分经 [`eval/image_search.py`](../../ai/eval/image_search.py) 在 COCO 上评估后加入：分数 = 余弦 + 0.1 × 两张照片物品的加权 Jaccard 重叠度（每类取分数 ≥ 0.3 的最高框分）。加权后“人”这类常见物品不会主导，平均精度从 0.551 升到 0.612、前 10 张的准确率从 78.4% 升到 81.9%（官方导出的模型，与社区转换版相同）。
- 界面：查看器加“找相似”（快捷键 S），结果复用照片网格，见[相册界面规格](../specs/photo-gallery-ui.md#物体检测与找相似2026-10-13)。

### 用图库外的图片搜索

2026-10-13 起，图库外的图片也能作为搜索条件（[界面](../specs/photo-gallery-ui.md#以图搜图2026-10-13)）。代码见 [`imagesearch.go`](../../internal/photos/imagesearch.go)。

- **接口**：
  - `POST /api/v1/photos/image-searches` 接收 multipart 的 `file`（JPEG 或 PNG，至多 32 MiB、2²⁶ 约 6700 万像素），识别后返回 `{id}`。
  - `GET /api/v1/photos/image-searches/{id}/assets?viewing=&cursor=&limit=` 按游标列出结果。
  - 只有发起的成员能读，其他人与过期一样得到 `404 search_expired`。范围在每次读取时按调用者重新计算，与搜索相同。
  - 识别要几秒，所以分成两个请求：后续翻页、从查看器返回都不必再识别一次。
- **识别**：
  - 相册服务按照片的做法渲染这张图片：解码一次，按 EXIF 转正、合成白底，得到 512 px 缩略图（`thumbnail/v1` 的参数）和长边 1600 px 的检测输入。两者都以密封的 `memfd` 交给 Worker，向量与图库照片的向量可比。
  - 先 `embed_image`。Worker 有检测器、且检测器正是阈值所校准的模型时再 `detect_objects`；检测失败或模型不符时只按向量排序，与尚未检测的照片一样。
  - 排序与“找相似”共用 `likeHits`：余弦 + 0.1 × 物品加权 Jaccard 重叠度，至多 500 张。图库里的同一张图不排除，排在最前。
- **不保存**：
  - 图片只在请求期间留在相册服务的内存里，不写入数据卷与暂存目录，也不记日志。
  - 保存的只是向量、模型名与每类的最高检测分，放在内存中，最后一次读取后 30 分钟过期，至多 64 个，满了先丢最久未用的。
  - 相册服务重启也会丢掉它们，浏览器收到 `search_expired` 后重新发送同一张图片。
- **资源**：
  - 同一时刻只识别一张图片：Worker 本来就一次只服务一个连接，解码大图又要几百 MB。像素上限低于导入时的 2²⁸，因为解码发生在有人等待的请求里。
  - 这是前台请求：它关闭 AI 门控，正在进行的后台检测会被取消，至多等一个无法中途取消的向量任务。
  - 检测器按需加载后，由后台任务的下一轮按“有人使用设备”卸载（`releaseModels`）。
- **错误**：
  - 不是可解码的 JPEG/PNG 返回 `415`，超出大小返回 `413`。
  - Worker 不可用返回 `503 ai_unavailable`，界面写“暂时无法识别图片，请稍后再试”。

## 资源策略

`CPUQuota=200%` 与“每次只让一个模型族常驻”来自[相册技术设计](photo-library.md)的初始预算，文档写明是“安全起点，不是实机结论”，内置 AI 时原样写进了单元，此后没有复核。用户原则（2026-10-13）：闲时有多少资源就用多少，始终保留余量，用户有突发请求时正确释放。“空闲 5 分钟后开始”出自规格，与“闲时”一致，保留。

- **CPU**：去掉固定的 `CPUQuota=200%`。推理线程数取可用逻辑核数减 2（i3-12100 为 6），留出一个物理核给突发请求；Worker 启动时从 `sched_getaffinity` 读取核数，MediaPipe 的线程数不可配置时如实记录。安装器按 `nproc` 写入 `anas-ai.service.d/cpu-reserve.conf`，以 `CPUQuota=(N−2)×100%`（至少 100%）兜底。
  - **低权重放在 `anas.slice`**（`CPUWeight=10`、`IOWeight=10`）：cgroup 只在兄弟之间比较权重，所以要放在与 `system.slice`、`user.slice` 平级的这一层，争用时设备上的其他工作先拿到核。最初写在 Worker 自己的单元里，那里它没有兄弟，实机首次运行时没有起作用。
  - `IOWeight` 只在 BFQ 或 `io.cost` 下生效，实验 NAS 数据盘用的 `mq-deadline` 下不起作用。
  - ONNX Runtime 的空闲线程不自旋。开发机上对照一个类似控制台的负载，自旋让每张的 CPU 时间和该负载等核的时间都多出数倍，检测本身也更慢（[调查](../investigations/2026-10-13-idle-detection-used-one-core.md)）。
- **门控看别人的压力**（2026-10-13 修订）：
  - 原来读全系统的 PSI，CPU 超过 20% 就关闭。这把 Worker 自己的线程互相等待也算进去，Worker 用满核数减 2 后可能把自己停住；开发机上压力在 20% 附近徘徊时，检测约每 8 秒被取消一次。
  - 现在 Worker 运行在自己的 `anas-ai.slice`（systemd 按名字里的“-”把它放在 `anas.slice` 之下，与 `system.slice` 平级）。门控读同一 systemd 下 `system.slice` 与 `user.slice` 的 PSI，取较高者，也就是相册、产品服务、SMB、控制台、容器与媒体转码这些设备上其他工作排队的时间。
  - 上限 CPU 10%、I/O 10%、内存 5%（过去 10 秒的 `some avg10`）；越过后要降到一半以下才重新打开（回滞），避免反复开关。都是初值，部署后实测再定。
  - 因 CPU 或 I/O 压力暂停后，每 5 秒复查一次（内核每 2 秒更新一次 10 秒均值），压力降到一半以下就恢复，被中止的任务先做。有人使用相册后的 5 分钟安静期和内存暂停仍每分钟复查：内存暂停已卸载模型，频繁复查会反复加载。
  - 门控每次因压力或内存不足关闭、重新打开时记一条日志：资源、10 秒均值与上限，以及每个被观察的 slice 的压力和其中等得最久的三个成员。实机上靠它判断是谁的工作让 AI 停下，再调上限。
  - 相册服务启动时在日志中写明读的是哪些 cgroup；不在 systemd 服务中（如开发时直接运行）时退回全系统的压力。
  - 本地栈实测（2026-10-13，开发机 14 个逻辑核，Worker 12 个线程，其他负载空闲）：整理 40 张新照片约 2 分钟，没有一次暂停或取消；`system.slice` 的压力最高 2.0%，整机最高 7.4%。
  - 实机首次运行（2026-10-13）没有达到目标：检测被取消 17 次，每次之后空等至少 1 分钟，Worker 平均只用了约 1 个核（[调查](../investigations/2026-10-13-idle-detection-used-one-core.md)）。[#88](https://github.com/zhongwater123/A-NAS/pull/88) 改为上面的做法（5 秒复查、`anas.slice` 的权重、渲染与推理重叠、线程不自旋），实机复测待部署。
- **内存**：检测器只在有检测任务时加载；检测队列清空或有人使用设备时，相册服务发 `release` 卸载检测会话（约 380 MiB）。CPU 或 I/O 压力只取消正在进行的检测、不卸载：取消已经让出处理器，卸载后压力一过又要重新加载，压力反复时大部分工作都花在加载上。内存吃紧时卸载全部模型，Worker 随即直接退出，不逐个析构模型（[调查](../investigations/2026-10-13-ai-worker-kept-cancelled-detector-sessions.md)）。向量模型因为搜索要用，保留到现有的 10 分钟空闲超时。内存吃紧指 PSI memory 超过阈值或系统 MemAvailable 低于余量（初值 1.5 GiB，实测后定），此时门控关闭并请求卸载全部模型，之后的搜索重新加载、多等几秒。单元加 `MemoryHigh=1792M` 让内核先回收，`MemoryMax=2G` 保留为硬上限，部署后按两个模型都加载时的 `MemoryPeak` 调整；真实模型的系统测试会打印它。
- **突发请求时**：前台请求关闭门控，不再领取新任务（已有）；正在执行的检测任务被取消并退回队列，不计尝试次数；正在执行的向量任务只能等它完成（用满线程后约 1 秒，实测验证）。前台搜索编码查询时，至多等一个无法取消的向量任务；目标是后台带来的额外等待不超过约 1 秒，达不到再给查询单独一条路径。

## 交付

- **模型清单** `deploy/models/dfine-m-obj365.json`：来源、revision、文件、大小、SHA-256，并存档许可证全文与作者对 Objects365 权重的声明。
- **运行环境**：`ai/requirements.txt`（当时为 `requirements.lock`）加 `onnxruntime==1.31.0` 与 `protobuf`（wheel 约 24 MB），在 `--no-deps` 下核实没有其他依赖；运行环境 ID 随之变化。
- **按角色泛化**：安装器、`remote-activate-release.sh`、`deploy-dev.ps1` 与系统测试从“一个模型”改为按角色处理（`model` 为 litertlm，`detector` 为 onnx，release 中链接为 `ai/detector.onnx` 与 `ai/detector.json`），以后人脸模型只需再加一个角色。
- **系统测试**：替身检测器文件；模型条目数 1→2、升级检查 2→3；篡改的检测器被拒绝；用替身完成一次检测；沙箱探针照常通过；核对单元的资源限制与安装器写入的 drop-in。为了在测试中看到照片整理完成，相册服务读取 `ANAS_PHOTOS_AI_QUIET_PERIOD`（如 `2s`）缩短空闲期，系统测试经 drop-in 设置，产品不设置。真实模型的运行由 `ANAS_AI_DETECTOR` 指定检测器文件。

## 风险

- 导出的模型与已评估的社区转换不一致；第 2 步是关口。
- 内存：EmbeddingGemma 在 NAS 上峰值 815 MB，加检测器约 380 MiB，`MemoryMax=2G`；内存超限被杀会消耗任务尝试次数，部署后实测。开发机上真实模型的系统测试（Debian 13 容器，2026-10-13）在两个模型都加载、整理完一张照片后 `MemoryPeak` 为 1.65 GiB，含模型文件的页缓存，低于 `MemoryHigh`（1.75 GiB）但余量不大；同一模型在开发机上的内存本来就比实机高（1.2–1.4 GiB 对 815 MB）。
- 1200 万像素照片缩到 640 后小物体更小；切片推理待真实照片评估。
- 2 万张的积压在原来 2 核上限下约需 8–15 小时空闲时间，放开到 6 线程后应明显缩短，以实测为准；最早的照片先处理。
- 超线程的兄弟核仍会互相拖慢，所以留出一个完整的物理核；向量任务无法中途取消，突发延迟以实测为准。
- 中文表的同义词猜错会让融合或分段用在错误的查询上；名单只启用评估过的类别。
